# TF2 Trade Suite Tools — Development notes

> Это внутренняя техническая документация проекта (архитектура, история
> реализации, обоснование каждого решения) — только на русском. Если вы
> ищете, что такое это расширение, какие в нём функции и как его
> установить, откройте главный [README.md](../README.md) (доступен на
> русском и английском).

Кроссбраузерное расширение для TF2-трейдинга на WXT + TypeScript + Vue 3.
Собственный аналог трёх изученных проектов (tf2trader, tf2TradingUtils,
Steam Trade Offer Enhancer 2.2.8), построенный так, чтобы удовлетворять
шести требованиям из ТЗ:

1. **Настройка расширения** — каждая функция включается/выключается
   отдельным тумблером, функции сгруппированы блоками по сайту.
2. **Единый визуал** — все элементы, которые расширение добавляет на
   страницу, используют один набор CSS-токенов (`styles/tokens.css`).
3. **Любой браузер** — WXT собирает один код в Chrome/Edge/Brave/Opera
   (MV3) и Firefox (MV2) сборки.
4. **Без дублирования функционала** — единый реестр модулей
   (`utils/registry.ts`) с полем `portedFrom`, которое явно фиксирует, из
   какого исходного проекта портирована каждая функция — это исключает
   реализацию одного и того же под разными именами.
5. **Новая функция — сводка валюты** — во время трейда показывает,
   сколько ключей/rf/rec/scrap лежит во ВСЁМ инвентаре (кошельке) у вас и
   у партнёра. Этой функции не было ни у одного из трёх изученных
   проектов.
6. **Иконки предметов** — база (unusual/strange/uncraft, определение
   атрибутов из сырых данных Steam) портирована точь-в-точь из Steam TO
   Enhancer. Поверх неё добавлена расширенная функция сверх ТЗ: у
   spell/killstreak значков есть переключаемый режим «Подробно» —
   конкретный спелл/тир/sheen/killstreaker собственными SVG-иконками
   (не просто общий бейдж, как в оригинале), с честным «Просто» как
   запасным вариантом без риска ошибки. Реализовано для окна
   трейд-оффера (`trade-item-attributes`), инвентаря
   (`inventory-item-attributes`) и листингов Steam Market
   (`market-item-attributes`) общим рендерером — см. ниже.

## Статус на данный момент

Все 22 функции реестра (`utils/registry.ts`) реализованы и включены в
сборку. Изначально функции делались **по одной**, чтобы каждую было легко
проверить перед следующей, а нереализованные пока держались в реестре со
статусом `planned` (тумблер уже виден и сохраняет выбор, сам модуль ещё
не написан) — на момент этого README таких не осталось: последние 4
`planned`-модуля (`copy-item-name`, `inventory-item-links`,
`bptf-profile-links`, `bptf-keys-total`) по прямой просьбе пользователя
убраны из реестра вместе с остальными нереализуемыми функциями, а не
оставлены висеть в `planned` навсегда — см. «Функции, которые решено не
реализовывать» в конце README. Раз делить больше нечего, отдельная плашка
«Готово»/«В планах» на карточках настроек и счётчик «в roadmap» из
шапки страницы настроек тоже убраны как утратившие смысл.

- `wallet-summary` — сводка валюты в трейд-оффере.
- `trade-item-attributes` — иконки/рамки предметов в оффере.
- `inventory-item-attributes` — те же иконки в инвентаре Steam.
- `market-item-attributes` — те же иконки в листингах Steam Market
  (классический дизайн и бета, см. ниже).
- `inventory-currency-counter` — счётчик валюты, встроенный в дизайн
  страницы инвентаря.
- `trade-item-summary` — сводка валюты по каждой стороне ТЕКУЩЕГО оффера,
  под аватарами.
- `pricedb-check-button` — кнопка "Проверить цену на PriceDB.io" в
  панели выбранного предмета инвентаря.
- `market-pricedb-check-button` — та же проверка цены, но у каждой
  строки листинга Steam Market.
- `quick-add-items` — панель Add Items/Keys/Metal/Recent/Clear в окне
  оффера.
- `auto-fill-from-listing` — полностью автоматическое добавление
  предмета И валюты по ссылке с backpack.tf, без кликов.
- `listing-price-button` — независимая ручная кнопка "Добавить цену
  объявления", отдельный тумблер от автозаполнения.
- `bptf-listing-trade-params` — дописывает цену/тип объявления в ссылку
  на трейд-оффер на backpack.tf.
- `offer-currency-total` — двухколоночная сумма валюты в списке
  офферов/истории.
- `offer-item-summary` — группировка одинаковых предметов, бейдж ×N, в
  списке офферов/истории.
- `stn-item-links` — кнопка "Проверить на PriceDB.io" на странице
  предмета stntrading.eu.
- `scrap-item-modal` — плавающее окошко "Проверить на PriceDB.io" по
  настраиваемой комбинации клика на предмет scrap.tf.
- `steam-profile-links` — ссылки на backpack.tf/steamhistory.net/posts.tf
  + бейдж SteamID64/32/классического на странице профиля Steam.
- `instant-accept-decline` — кнопки "Принять"/"Отклонить" прямо в списке
  входящих офферов, без перехода на страницу оффера.
- `decline-all-active` — одна кнопка над списком, отклонить сразу все
  активные входящие офферы, с подтверждением.
- `bptf-ks-tier-buttons` — кнопки переключения килстрик-тиров No Kit/
  Killstreak/Specialized/Professional на classic backpack.tf `/stats` и
  `/classifieds`, плюс фильтр по Sheen/Killstreaker.
- `bptf-filter-special` — кнопки «Только spells»/«Только strange parts»
  над списком объявлений на classic backpack.tf.
- `bptf-price-graph` — график цены PriceDB.io на странице `/stats`,
  перед Classifieds, в нативном стиле backpack.tf.

**Экспериментально: поддержка бета-дизайна Market.** У Steam Market есть
отдельный "бета"-режим (кнопка "Выйти из бета-теста торговой площадки" в
шапке страницы; статья Valve подтверждает, что бета включена по умолчанию
всем, без ручного opt-in) с полностью другим React SPA-рендером
(`window.SSR`, хэшированные CSS-модули вместо обычных классов). Живой
проверкой на реальной странице `market/listings/440/<предмет>` найден
рабочий источник данных — тот же API, что использует сама бета-страница
(`/market/actions?q=QueryListingsForItem`), отдающий assetId и полное
описание предмета, как и на остальных трёх модулях (см.
`utils/market-beta-watch.ts` — перенесён туда из `modules/market-item-attributes/`,
когда понадобился второму модулю, `market-pricedb-check-button`, см. ниже).
**Но** есть принципиальное
отличие от всех остальных модулей: в разметке беты нет НИКАКОГО
идентификатора листинга на карточке (ни id, ни data-атрибута — только
хэшированные классы) — единственный способ сопоставить карточку в DOM с
данными из API это ПОРЯДОК (карточка №N на странице = запись №N в ответе
API), а не точное совпадение по id. Сработает в подавляющем большинстве
случаев (карточки добавляются в грид строго в том же порядке, что и ответ
API, бесконечная подгрузка только дописывает в конец), но теоретически
может один раз "поехать", если Valve перепишет рендер без сохранения
порядка — риск принят осознанно (обсуждён и подтверждён пользователем).
Классическая страница продолжает работать точным сопоставлением по id, как
и раньше — оба пути живут в одном модуле и не мешают друг другу (см.
`apply.ts`: `scan()` для классики, `scanBeta()` для беты, второй скан на
классической странице — дешёвый no-op, и наоборот).

## Архитектура

### Структура каталогов

```
entrypoints/            — точки входа WXT (content-скрипты, popup, options)
  tradeoffer-wallet-core.content.ts   MAIN-world: читает window.UserYou/UserThem
  tradeoffer-wallet.content.ts        ISOLATED-world: рисует UI, слушает настройки
  popup/                              всплывающее окно расширения
  options/                            страница настроек (Vue)
modules/<feature-id>/    — один модуль = одна функция
  core.ts                MAIN-world логика (если нужен доступ к window.* страницы)
  panel.ts / panel.css   ISOLATED-world UI модуля
  types.ts               общий контракт запрос/ответ моста между мирами
utils/
  registry.ts             реестр всех функций (единственный источник правды)
  settings.ts             storage-обёртка над реестром (вкл/выкл + реактивность)
  bridge.ts                постMessage RPC между MAIN и ISOLATED world
  currency.ts              defindex-константы и арифметика валюты TF2
  inventory-fetch.ts        постраничный fetch инвентаря Steam + подсчёт валюты
styles/tokens.css        — единая дизайн-система (CSS-переменные, .tf2s-root)
components/               переиспользуемые Vue-компоненты для options
public/icon/               иконки расширения (16/32/48/96/128)
```

### Почему MAIN + ISOLATED, а не один content-скрипт

Steam кладёт нужные данные (`window.UserYou`, `window.UserThem`,
`window.g_rgCurrentTradeStatus`) в **JS-контекст самой страницы**, а не в
DOM. Content-скрипт в изоляции (`world: 'ISOLATED'`, дефолт) их не видит.
Поэтому:

- `*-core.content.ts` инжектится с `world: 'MAIN'`, читает `window.*`
  страницы и отвечает на запросы через мост.
- `*.content.ts` (без `-core`) остаётся `ISOLATED`, монтирует UI через
  `createShadowRootUi` (полная изоляция стилей от хост-страницы) и
  запрашивает данные у MAIN-скрипта через `utils/bridge.ts`.

Мост (`utils/bridge.ts`) — общий для всех модулей: `window.postMessage` с
namespace `__tf2suite__`, сопоставление запрос/ответ по UUID, таймаут.
Раньше в трёх исходных проектах было по отдельной реализации моста в
каждом — здесь она одна и переиспользуется.

**Важно:** MAIN-скрипты никогда сами не проверяют, включена ли функция —
у них нет доступа к `browser.storage`. Решение о том, показывать ли UI,
принимает исключительно ISOLATED-скрипт (`isFeatureEnabled` +
`watchSettings`), поэтому выключение функции в настройках гасит её сразу,
без перезагрузки страницы.

### Реестр функций (`utils/registry.ts`)

`FEATURE_REGISTRY` — массив из 22 объектов `FeatureModule`, все со
статусом `status: 'ready'` — ни одной `planned`-функции не осталось (были
изначально, реализовывались по одной, см. «Статус на данный момент»
выше). Всего 14 когда-то запланированных функций по прямой просьбе
пользователя решено не реализовывать вовсе и убрать из реестра целиком, а
не просто оставить висеть в статусе `planned` навсегда — см.
doc-комментарий над `FEATURE_REGISTRY` и «Функции, которые решено не
реализовывать» в конце README за полным списком. Каждый оставшийся
объект:

- `id` — уникальный ключ (используется в storage и как имя папки в `modules/`).
- `site` — один из 8 `SiteGroup` (Steam trade offer, список офферов,
  инвентарь, маркет, backpack.tf, scrap.tf, stntrading.eu, профиль Steam).
- `title`/`description` — теперь `LocalizedText` (`Record<'ru' | 'en', string>`,
  см. «Локализация» ниже), а не голая строка — читаются через `t(locale, ...)`.
- `defaultEnabled` — состояние тумблера по умолчанию.
- `status: 'ready' | 'planned'` — тип по-прежнему поддерживает оба
  значения (задел на будущие модули), но сейчас у всех 22 объектов
  реестра `'ready'`; раз делить нечего, отдельная плашка «Готово»/
  «Скоро» на карточке настроек и счётчик «в roadmap» в шапке страницы
  настроек убраны как утратившие смысл (см. `FeatureToggle.vue`/
  `App.vue`) — появятся снова, если/когда в реестре опять будет хотя бы
  один `planned`-модуль.
- `stability?` — необязательный `LocalizedText` с предупреждением об
  известном ограничении/нестабильности функции (например, у
  `bptf-price-graph` — график PriceDB.io есть не для каждого предмета; у
  всех модулей проверки цены на PriceDB.io — общая формулировка через
  `PRICEDB_NAME_LOOKUP_CAVEAT`, не дублируется по функциям). Рендерится
  отдельным предупреждением на карточке в `FeatureToggle.vue`, отдельно от
  обычного описания.
- `dependsOn?: string[]` — необязательный список `id` функций, от которых
  зависит эта. Механизм подготовлен по прямой просьбе пользователя
  («предупреждение, если от какой-то функции есть зависимость к другой»),
  но сейчас у ready-функций реальных зависимостей друг от друга нет
  (проверено — ни один модуль не импортирует `core.ts`/`apply.ts` другого
  модуля), поэтому поле остаётся пустым везде; когда оно появится у
  какого-то модуля, `FeatureToggle.vue` сам покажет предупреждение
  «Требует: …» со списком заголовков зависимостей на текущем языке.
- `portedFrom` — из какого исходного проекта портирована функция (или
  «новая функция», как у `wallet-summary`). Это и есть механизм
  требования 4 — прежде чем добавить новый модуль, легко проверить по
  этому полю, не реализовано ли уже что-то похожее. Поле по-прежнему
  заполняется у каждого модуля, но по прямой просьбе пользователя больше
  НЕ рендерится отдельной плашкой на каждой карточке настроек — вместо
  этого внизу страницы настроек единый блок благодарностей со списком
  использованных проектов (`CREDIT_PROJECTS`, см. «Локализация» ниже).

Настройки (`utils/settings.ts`) хранят `Record<featureId, boolean>` плюс
`locale: 'ru' | 'en'` в `browser.storage.local`, с дефолтами из реестра
(язык по умолчанию — русский) и версионированной миграцией
(`storage.defineItem` из `wxt/storage`, старые сохранённые настройки без
`locale` домердживаются дефолтом при чтении). Options-страница и popup
читают тот же реестр, так что при добавлении нового модуля в
`FEATURE_REGISTRY` тумблер в UI появляется автоматически — ничего в
Vue-компонентах менять не нужно.

### Единый визуал (`styles/tokens.css`)

Все инжектируемые элементы обёрнуты в `<div class="tf2s-root">` внутри
shadow root (`createShadowRootUi`), что даёт полную изоляцию и от, и в
CSS хост-страницы. Токены — цвета (включая палитру качества предметов
TF2: unusual/strange/vintage/genuine/...), радиусы, тени, отступы, шрифт
— объявлены на классе `.tf2s-root`, а не на `:root`, специально чтобы не
вытекать наружу. Готовые переиспользуемые классы: `.tf2s-panel`,
`.tf2s-btn` (+ `--accent`, `--icon`), `.tf2s-badge`, `.tf2s-link`,
`.tf2s-muted`. Любой новый модуль обязан использовать эти классы/токены
вместо своих цветов.

### Локализация (`utils/i18n.ts`) и чистка настроек

По прямой просьбе пользователя расширение полностью двуязычное — русский
(язык по умолчанию) и английский, переключается на странице настроек и
применяется сразу, без перезагрузки расширения.

- `utils/i18n.ts` — весь контракт: `Locale = 'ru' | 'en'`,
  `DEFAULT_LOCALE = 'ru'`, `LocalizedText<T = string> = Record<Locale, T>`
  и функция `t(locale, text)`, которая берёт нужный язык с фоллбэком на
  `DEFAULT_LOCALE`. `utils/settings.ts` хранит выбранный язык
  (`getLocale()`/`setLocale()`), реестр (`title`/`description`/`stability`
  в `utils/registry.ts`) и `SITE_GROUPS` целиком типизированы через
  `LocalizedText`.
- **Per-модульные словари, а не один общий файл.** Каждый модуль/компонент
  со своим UI-текстом держит маленький локальный `const UI = { ru: {...},
  en: {...} } as const` прямо рядом с кодом, который его использует — тот
  же принцип, что и у остальных плотных doc-комментариев проекта: контекст
  живёт там же, где используется, а не в одном разрастающемся файле-
  словаре на всё расширение. Названия самой игровой терминологии TF2 —
  Spell, Killstreak, Strange Part(s), тиры No Kit/Killstreak/
  Specialized/Professional, имена Sheen/Killstreaker — сознательно НЕ
  переводятся ни в русской, ни в английской локали: это те же термины,
  которыми оперируют сама игра, backpack.tf и исходные проекты, перевод
  добавил бы путаницы, а не ясности.
- **Как локаль доходит до content-скриптов.** У Vue-компонентов (options,
  popup) локаль — обычный реактивный `ref`, синхронизируется через
  `watchSettings`. Content-скрипты (`entrypoints/*.content.ts`) — не
  Vue-реактивны, поэтому каждый `start<Модуль>(...)` получает `locale`
  последним параметром, а `watchSettings` в entrypoint'е при смене
  `settings.locale` делает **полный `stop()` + повторный `start(locale)`**
  — тем же путём, что и обычное включение/выключение фичи. Для модулей с
  постоянно смонтированной shadow-root-панелью (`createShadowRootUi`) —
  тот же принцип, но `ui.remove()` + `ui.mount()` вместо `stop()`/`start()`
  (а если у модуля есть live-опции без пересоздания DOM, как `setMode`/
  `setOptions` — типа `trade-item-summary`/`auto-fill-from-listing` — их
  всё равно недостаточно: у обоих модулей текст сообщений формируется
  внутри `MutationObserver`/поллинг-колбэков с `locale`, захваченной в
  замыкании при монтировании, так что смена языка тоже требует полного
  remount, а не только `setMode`/`setOptions`). Решение намеренно
  единообразное для всех ~20 entrypoint'ов, а не point-оптимизация под
  каждый модуль отдельно — ниже риск ошибиться, проще поддерживать.
- **`FeatureModule.stability`** — необязательный `LocalizedText`,
  предупреждение о конкретном известном ограничении функции, показывается
  на карточке настроек отдельно от обычного описания (по прямой просьбе
  пользователя, с примерами `bptf-price-graph`/PriceDB.io-модулей из
  исходного сообщения). Общая для всех PriceDB.io-модулей с проверкой цены
  по имени формулировка («не учитывает parts/spell/вариации sheen и
  killstreak-тира при точном сопоставлении») вынесена в один общий
  константный текст `PRICEDB_NAME_LOOKUP_CAVEAT` и переиспользуется у
  `pricedb-check-button`, `market-pricedb-check-button`,

### Модуль `quick-add-items` (готовый)

Панель управления офферу — Add Items / Keys / Metal / Recent (с полями
"количество"/"индекс"), очистка своей/чужой стороны. Портировано из

`src/js/steamcommunity.com.tradeoffer.js` — оригинал изучен вживую, не по
памяти): функции `collectItems` (подбор предметов по режиму) и
`addItemsByElements`/`clearItemsInOffer` (запись в состояние оффера).

**Режима "добавить по списку ID" (был в оригинале, хоткей «P») здесь
намеренно нет** — убран по прямой просьбе пользователя как неудобное в
использовании поле: нужно было знать точный assetId предмета заранее, а
взять его было особо неоткуда без внешних инструментов (DevTools/ссылки с
маркетплейсов). Замена уже реализована — см. §"Модуль `auto-fill-from-
listing`" ниже: он САМ читает `for_item=` из ссылки backpack.tf и добавляет
нужный предмет, без ручного ввода ID пользователем.

**Почему это единственный модуль страницы оффера, который MAIN world не
только ЧИТАЕТ, но и МЕНЯЕТ.** `wallet-summary`/`trade-item-attributes`/
`trade-item-summary` только читают `window.g_rg*` — здесь нужно ещё и
дописать/убрать предметы в `window.g_rgCurrentTradeStatus.me/them.assets` и
вызвать `window.RefreshTradeStatus(...)`. Этот API существует только в
JS-контексте самой страницы, поэтому архитектура та же, что и у остальных
модулей оффера (ISOLATED — UI, MAIN — работа с состоянием через
`utils/bridge.ts`), просто канал в этот раз не read-only:

- `modules/quick-add-items/types.ts` — контракт RPC (`QuickAddRequest` с
  режимом `ITEMS | KEYS | METAL | RECENT | CLEAR_ME | CLEAR_THEM`, канал
  `tf2suite:quick-add-items`).
- `modules/quick-add-items/core.ts` (MAIN world) — собственно порт:
  - `pickItemsForSide` — выбор до N подходящих предметов начиная с позиции
    `index` среди ещё НЕ добавленных в оффер (портировано из `collectItems`'s
    `pickItems`). **Исправленный баг оригинала**: подстраховка "не хватило по
    индексу — сдвинуть окно назад" в исходнике написана как `if (items <
    amount)` — сравнение МАССИВА с числом; из-за приведения типов JS это
    условие истинно только когда `items` **пустой** (`[].toString() === '' →
    0 < amount`), а не когда его длина меньше `amount`, как явно задумано
    соседним кодом/комментариями оригинала. Здесь — `items.length < amount`,
    как и должно быть.
  - `getItemsForMetal` — жадный подбор Refined→Reclaimed→Scrap на сумму в
    ref, использует `utils/currency.ts#refinedValueToScrap`/`METAL_SCRAP_VALUE`
    (арифметика специально была отложена в currency.ts до этого модуля, см.
    комментарий там же — требование 4).
  - Режим `RECENT` ("Недавние") — портированный `getNearNumbers`: находит
    группу предметов с ПОСЛЕДОВАТЕЛЬНО близкими assetId (обычно значит "из
    одного дропа/трейда").
  - `addItemsByElements` — читает `elItem.rgItem`, JS-свойство, которое сам
    Steam вешает на DOM-узел предмета (НЕ HTML-атрибут) — видно только из
    MAIN world, того же JS-реалма, что и собственные скрипты страницы.
  - **appid/contextid захардкожены на TF2 (440/2) для KEYS/METAL**, но НЕ
    для ITEMS/RECENT — те просто берут то, что сейчас видно на экране (как в
    оригинале), а "Ключи"/"Металл" должны искать именно TF2-предметы
    независимо от того, какая вкладка инвентаря сейчас открыта (оригинал —
    универсальный под любую игру Steam; TF2 Trade Suite Tools — нет, см. README целиком).
- `modules/quick-add-items/panel.ts` (ISOLATED world) — UI: поля
  количество/индекс, кнопки режимов. Единственная панель проекта с
  текстовыми полями, которые пользователь активно печатает — поэтому, в
  отличие от `wallet-summary` (полный `innerHTML` на каждое изменение
  состояния), разметка строится **один раз** при монтировании, а дальше
  меняется только сообщение статуса — иначе перерисовка на каждое нажатие
  клавиши сбрасывала бы курсор/фокус в поле ввода.
- Панель встраивается ВНУТРЬ `#inventory_box div.trade_box_contents` —
  классическая (не React) разметка страницы оффера, присутствует в исходном
  HTML при загрузке, тот же контейнер, куда оригинал добавляет свою панель;
  в отличие от React-панели предмета в инвентаре (`pricedb-check-button`) не
  нужен пересчитываемый на каждый ремонт якорь — обычный строковый селектор,
  как у `wallet-summary`.
- Кнопки "Очистить мои"/"Очистить партнёра" — часть той же цельной панели,
  что и в оригинале (не отдельный модуль): в справочном проекте это те же
  кнопки того же управляющего блока, что и Add Items/Keys/Metal.

**ИСПРАВЛЕННЫЙ БАГ (баг-репорт пользователя): кнопки "Очистить" не
работали.** Оригинал (`clearItemsInOffer`) убирает предметы через
`window.GTradeStateManager.RemoveItemsFromTrade(items)` — недокументированный
внутренний API самого Steam, отдельный от того способа, которым добавляются
предметы. Судя по симптому (Add работает, Clear — нет), эта функция сейчас
либо отсутствует, либо ведёт себя иначе, чем на момент написания оригинала —
а вызов через `?.()` в этом случае просто молча ничего не делает, без единой
ошибки в консоли, поэтому баг было не сразу заметно. **Исправление**: вместо
повторной попытки угадать актуальное имя внутреннего API — тот же приём, что
уже доказанно работает у `addItemsByElements` (добавление): напрямую чистим
массив `assets` нужной стороны в `window.g_rgCurrentTradeStatus` и зовём
`window.RefreshTradeStatus(...)` — тот же источник правды, которым Steam и
так перерисовывает слоты оффера, без зависимости от `GTradeStateManager`.
Заодно панель теперь показывает сообщение об ошибке, если очистка всё же не
удалась (раньше ЛЮБАЯ ошибка тут проглатывалась молча — выглядело как
"кнопка не реагирует").

**ВТОРОЙ ИСПРАВЛЕННЫЙ БАГ (второй баг-репорт): очистка оставляла пустую
ячейку в окне выбора предметов на месте некоторых предметов.** Сам оффер
очищался корректно, но карточка предмета в инвентаре не возвращалась на
место — оставалась пустой, как будто предмет всё ещё числится "уже
предложенным". Причина: предыдущий фикс писал `tradeSide.assets = []` —
заменял ссылку на массив НОВЫМ объектом. А `addItemsByElements` добавляет
предметы через `slots.push(...)` — то есть МУТИРУЕТ тот же самый массив,
никогда не заменяя ссылку. Судя по всему, что-то во внутренней логике Steam
(которая решает, какие тайлы в окне выбора сейчас скрыты как "уже
предложены") держит СВОЮ собственную ссылку именно на этот массив-объект —
замена ссылки на новый пустой массив эту логику не находила и оставляла
тайл скрытым. **Исправление**: очищаем массив НА МЕСТЕ
(`tradeSide.assets.length = 0`), сохраняя объект-ссылку.

**ТРЕТИЙ ИСПРАВЛЕННЫЙ БАГ (третий, четвёртый и пятый баг-репорты): тот же
симптом остался ПОСЛЕ фикса выше, без чёткой зависимости от количества**
(например, из 10 очищенных не возвращались 2 тайла, из 11 — 3). Две попытки
чинить это подряд **НЕ ПОМОГЛИ**: (а) несколько проходов `RefreshTradeStatus`
с задержкой (0/80/400 мс); (б) форс-перерисовка окна выбора тем же приёмом,
что `forceVisibility()` в оригинале — клик по неактивной вкладке инвентаря и
сразу обратно на активную. Обе попытки исходили из предположения, что не
хватает ЕЩЁ ОДНОЙ перерисовки/задержки — предположение оказалось неверным.

Ключевые улики (пятый баг-репорт): (1) пропадают всегда именно первые ≈8
тайлов сверх какого-то порога — 10 предметов → пропадает 2 (10-8), 11 → 3
(11-8); (2) обычная перезагрузка страницы (F5, без переоткрытия оффера)
ВСЕГДА возвращает все пропавшие тайлы на место. Вместо очередной догадки
пользователя попросили выполнить в консоли DevTools скрипт-диагностику сразу
после очистки:

```js
(() => {
  const s = window.g_rgCurrentTradeStatus;
  console.log('me.assets:', s?.me?.assets?.length, JSON.stringify(s?.me?.assets));
  console.log('them.assets:', s?.them?.assets?.length, JSON.stringify(s?.them?.assets));
  console.log('DOM items in your_slots:', document.querySelectorAll('#your_slots .item').length);
  console.log('DOM items in their_slots:', document.querySelectorAll('#their_slots .item').length);
})();
```

Результат оказался решающим: `me.assets`/`them.assets` — оба `0 []`, DOM
`#your_slots`/`#their_slots` — оба содержат 0 `.item`-элементов. То есть и
реальное состояние оффера (`g_rgCurrentTradeStatus`), и DOM самих слотов
оффера — ВСЕГДА полностью и корректно очищены, никакого рассинхрона там нет.
Значит, весь баг живёт ИСКЛЮЧИТЕЛЬНО в отдельном, недоступном напрямую
механизме окна выбора предметов, который отслеживает "этот тайл уже в
оффере, скрыть его" — судя по совпадению порога с дефолтной сеткой Steam
(2×4 = 8 слотов до её динамического роста), при массовом (bulk) изменении
разом этот механизм надёжно обрабатывает только первые ~8 изменений за
вызов, а остальные теряет — и ни повторные вызовы `RefreshTradeStatus`, ни
принудительная перерисовка вкладки эту внутреннюю недостачу не чинят,
потому что читают то же самое (уже полностью корректное) состояние.

**Исправление**: раз проблема именно в BULK-изменении, убираем предметы из
`assets` НЕ ОДНИМ массовым действием, а ПО ОДНОМУ — так же, как если бы
пользователь вручную перетаскивал их обратно по одному (единственное,
что доказанно работает надёжно всегда). После каждого отдельного `pop()` из
массива вызывается свой `RefreshTradeStatus(status, true)`, а перед
следующим удалением — пауза в один кадр отрисовки (`requestAnimationFrame`),
чтобы Steam успел обработать каждое изменение по отдельности, а не получить
их пачкой. Это гипотеза, основанная на диагностике выше, а не официально
подтверждённое поведение Steam (внутренний механизм окна выбора нигде не
задокументирован) — если после этого фикса всё ещё будут пропадать тайлы,
это будет ценно увидеть отдельно: пропадают ли теперь вообще при любом
количестве, или порог просто сдвинулся выше 8.

**Поле "индекс" — как им пользоваться.** Это не количество, а СМЕЩЕНИЕ: с
какого по счёту подходящего предмета начинать отсчёт (0 — с самого первого).
Например, "Ключи", количество=1, индекс=0 — добавит первый попавшийся ключ;
индекс=1 — пропустит первый и добавит следующий (второй) ключ. Отрицательный
индекс считает С КОНЦА списка: индекс=-1 — взять последний подходящий
предмет, индекс=-2 — предпоследний. Для большинства случаев (просто "добавь
мне N ключей/предметов откуда угодно") индекс можно оставить 0 — он нужен,
только когда важно пропустить какие-то конкретные экземпляры (у "Недавних"
это поле почти не играет роли — тот режим сам ищет группу предметов с
близкими ID, а не считает по порядку).

### Модули `auto-fill-from-listing` и `listing-price-button` (готовые)

Автозаполнение оффера по ссылке с backpack.tf — предполагавшаяся ещё при
удалении поля "ID" из `quick-add-items` замена (см. выше): не нужно знать
assetId предмета заранее, ссылка сама несёт всё необходимое. Портировано из
**Steam Trade Offer Enhancer** (тот же реальный исходник, что и
`quick-add-items` — клонирован повторно, изучен вживую): обработка
`urlParams.for_item`/`urlParams.listing_intent` в IIFE
`steamcommunity.com.tradeoffer.js` и функция `addListingPrice`/`addCurrencies`.

**Формат ссылки.** Кнопка перехода в трейд-оффер на странице
classifieds/профиля/статистики backpack.tf несёт в query-строке:

- `for_item=<appid>_<contextid>_<assetid>` — какой именно предмет партнёра
  имелся в виду. Кладётся самим backpack.tf (не расширением) и встречается
  ТОЛЬКО у объявлений на ПРОДАЖУ — у объявления на покупку нет одного
  конкретного экземпляра предмета (продавец сам решает, какой из
  подходящих отдать), поэтому туда предмет всегда добавляется в
  инвентарь ИМЕННО партнёра (`them.assets`), независимо от того, кто в
  итоге платит валюту.
- `listing_intent` — `0` (объявление на покупку) | `1` (объявление на
  продажу). Кодировка как у backpack.tf/оригинала.
- `listing_currencies_keys` / `listing_currencies_metal` — цена объявления
  в ключах/рефайнде.

Отсюда логика валюты (`isYou = listingIntent === 1`, портировано как есть):
при `listing_intent=1` (продажа) платим МЫ — партнёр отдаёт предмет,
который уже добавлен из `for_item`. При `listing_intent=0` (покупка) платит
ПАРТНЁР — а какой из своих предметов продать, пользователь выбирает сам
(например, кнопкой "Добавить" из `quick-add-items`).

**Не дублируем `quick-add-items` (требование 4).** Поиск ключей/металла по
инвентарю, добавление найденных элементов в оффер, форс-перерисовка и все
типы `window.g_rg*`/`g_rgCurrentTradeStatus` — та же самая логика, что нужна
и здесь (кнопка "Добавить цену объявления" — это, по сути, ещё один вызов
"добавь N ключей + X ref металла"). Вместо копирования это вынесено в общий
`utils/trade-offer.ts`, когда понадобилось во второй раз — `modules/quick-
add-items/core.ts` был переписан на импорт оттуда же (никакой логики не
менялось, только перенос: см. историю багов `clearSide` — она осталась
нетронутой и по-прежнему живёт в `quick-add-items/core.ts`, т.к. специфична
только для очистки). `utils/trade-offer.ts` — общие типы (`TradeOfferWindow`,
`SteamCurrentTradeStatus` и т.д.) и функции (`pickItemsForSide`, `findKeys`,
`getItemsForMetal`, `addItemsByElements`, `forceRefresh`, `nextFrame`).
`auto-fill-from-listing/core.ts` оставляет себе только то, что специфично
именно ему: добавление конкретного assetId из ссылки и подсчёт валюты по
цене объявления.

**Автодобавление `for_item` — без кнопки, само.** В отличие от
`quick-add-items` (пользователь явно жмёт кнопку), добавление предмета по
ссылке происходит сразу при открытии страницы — портировано как есть из
оригинала (там это тоже безусловный код в IIFE, а не обработчик клика).

**ДВА НЕЗАВИСИМЫХ ТУМБЛЕРА (изменение по прямой просьбе пользователя после
живого теста).** Изначально кнопка "Добавить цену объявления" была
реализована как часть одного тумблера `auto-fill-from-listing` — пользователь
явно попросил разделить: *«мне нужно чтобы это были отдельные функции
которые можно включать по отдельности. те включено Автозаполнение по ссылке
с backpack.tf но кнопка не включена и наоборот»*. Плюс отдельно попросил
сделать само автозаполнение полностью автоматическим — не только предмет, но
и валюту, вообще без клика. Теперь это два раздельных пункта в настройках
(общий код и RPC-канал, см. `types.ts`):

- **`auto-fill-from-listing`** — полностью автоматический режим: сам, без
  единого клика, опрашивает MAIN раз в секунду и добавляет предмет по
  `for_item` (только продажа — см. выше), валюту по цене объявления (ОБА
  вида объявлений) И, для покупки, свой предмет по `listing_item_name`, если
  совпадение в инвентаре однозначное (см. `findOwnItemByName` в разборе
  бага ниже). Раньше валюту добавляла только кнопка; теперь при включённом
  этом тумблере она тоже подставляется сама тем же стейтless-опросом, что и
  `for_item` (полезно для покупки: валюту кладёт партнёр, а его инвентарь
  тоже может подгружаться не сразу, поэтому нужны повторные попытки, а не
  одна).
- **`listing-price-button`** — независимая ручная кнопка "Добавить цену
  объявления": работает вне зависимости от того, включено ли автозаполнение.
  Можно включить только кнопку (без автоматики) или только автоматику (без
  кнопки), или оба сразу.

**Защита от задвоения валюты, когда включены ОБА тумблера.** Раз добавление
цены объявления теперь достижимо двумя независимыми путями одновременно
(автоопрос и клик по кнопке), наивная реализация ("всегда добавляй полную
цену объявления") задвоила бы валюту в оффере, если пользователь нажмёт
кнопку уже после того, как автозаполнение всё само добавило. Исправлено в
`core.ts`: `addListingPrice` теперь сначала считает, сколько нужной валюты
УЖЕ лежит в слотах (`getCurrentCurrency` — суммирует по `market_hash_name`
через тот же инвентарь, что использует поиск), и добавляет только
НЕДОСТАЮЩЕЕ — повторный вызов, когда всё уже добавлено, безопасный no-op.
Плюс `addListingPriceGuarded` — если запрос уже выполняется, второй
параллельный вызов (гонка между кнопкой и автоопросом ровно в один момент)
не считает свой отдельный шорт-фолл, а просто ждёт результата уже идущего.

**"Мёртвый" предмет (объявление уже продано/обменяно).** Оригинал ждёт
однократный колбэк `inventoryManager.register(...)`, который срабатывает
ровно один раз, когда инвентарь партнёра догрузится, и тогда уже проверяет
`page.get.$deadItem()` (`a[href$="_undefined"]` — Steam так помечает тайл,
который не смог сопоставить с реальным предметом). У TF2 Trade Suite Tools нет такого
колбэка: `utils/bridge.ts` — это ISOLATED-инициированный запрос/ответ, MAIN
не может САМ прислать пуш в ISOLATED, когда что-то случилось (см. её шапку).
Вместо одного колбэка — стейтless-опрос: ISOLATED раз в секунду спрашивает
MAIN "как там дела с этим предметом", MAIN каждый раз заново проверяет
текущее состояние (без собственной памяти между вызовами) и отвечает одним
из трёх: `pending` (инвентарь партнёра ещё не подгрузился — спросят ещё раз),
`added` (предмет нашёлся в уже загруженных данных партнёра — тихий успех,
дальше просто виден в слоте), `dead` (Steam отрисовал "мёртвый" тайл —
предмет убирается из оффера, пользователю показывается сообщение). Опрос
останавливается на первом окончательном ответе или через ~20 попыток (по
секунде).

**ИСПРАВЛЕННЫЙ БАГ (баг-репорт живым тестом: sell-order, предмет не
добавлялся вообще, без единого сообщения — по наблюдению пользователя, тот
конкретный экземпляр из объявления уже не в инвентаре бота, хотя другие
копии того же предмета там есть).** Раньше "мёртвость" определялась ТОЛЬКО
по DOM-признаку — предполагалось, что Steam рисует тайл-заглушку
(`a[href$="_undefined"]`), когда не может сопоставить assetid с реальным
предметом партнёра. На практике Steam для несуществующего assetId часто
вообще ничего не рисует — ни тайл, ни заглушку — поэтому DOM-признак не
срабатывал, и опрос молча зависал в `pending` до тайм-аута без единого
сообщения (то самое "тихо сдаёмся" из предыдущей версии этого абзаца).
**Исправление**: инвентарь партнёра Steam грузит целиком одним запросом на
контекст, а не по одному предмету — значит, если инвентарь по TF2-контексту
уже непустой (хоть один предмет там есть), он уже полностью загружен, и
если искомого assetId в нём всё равно нет — это гарантированно "его больше
нет", а не "ещё грузится". Теперь `checkForItem` в первую очередь опирается
на это (DOM-признак остался как дополнительная проверка), и по тайм-ауту
опрос тоже больше не молчит — показывает сообщение вместо того, чтобы тихо
сдаться.

**Кнопка "Добавить цену объявления"** показывается, только если включён её
тумблер (`listing-price-button`) И в ссылке есть `listing_intent` и хотя бы
одна из валют больше нуля. На обычных ссылках трейд-оффера (без параметров
backpack.tf) панель вообще не монтирует никакого UI, а если ни у одного из
двух тумблеров нет данных для показа (ни `for_item`, ни цена объявления) —
тоже (см. `panel.ts#mountAutoFillPanel`, решение зависит от содержимого самой
ссылки, а не от тумблеров), чтобы не добавлять лишний DOM на подавляющем
большинстве офферов. Если ссылка содержит нужные данные, но включённых
тумблеров нет вообще — UI тоже не монтируется (entrypoint сравнивает
`autoFillEnabled || priceButtonEnabled`), а при переключении любого тумблера
на лету (без перезагрузки страницы оффера) панель обновляется через
`setOptions`, не пересоздавая DOM.

**ИСПРАВЛЕННЫЙ БАГ (первый баг-репорт с живого теста): пустая "полоса" над
панелью `quick-add-items`, когда в ссылке есть `for_item`, но кнопки цены
нет.** `.tf2s-panel.tf2s-autofill` создавался ВСЕГДА, если было хоть что-то
(`for_item` ИЛИ кнопка цены) — а внутри нередко оказывался только СКРЫТЫЙ
(`hidden`) элемент сообщения без кнопки. У панели есть padding/margin (см.
`panel.css`) — они применяются к контейнеру независимо от того, скрыты ли
его дети, поэтому пустая на вид, но с реальными отступами область
оставалась видна как пустая полоса. Судя по первому же живому тесту это
довольно частый случай (ссылка есть `for_item`, но `listing_intent` нет —
см. следующий абзац). **Исправление**: панель теперь создаётся ЛЕНИВО —
только в момент, когда реально есть что показать (кнопка — сразу при
монтировании, если есть цена объявления; сообщение — только пока оно
активно), и удаляется, как только показывать больше нечего.

**ИСПРАВЛЕНО: кнопка цены и объявления на покупку не могли работать —
не хватало соседнего модуля (теперь он есть, см. ниже).** Второй
баг-репорт с живого теста: на Buy Order не добавился ни предмет из своего
инвентаря (это и не должно происходить автоматически — для покупки нет
`for_item`, предмет пользователь добавляет сам), ни валюта из инвентаря
партнёра (кнопки цены просто не было). Пользователь прислал реальные
ссылки для обоих случаев:

- Sell order: `.../tradeoffer/new/?partner=<id>&token=<token>&for_item=440_2_<assetid>`
  — есть `for_item`, и БОЛЬШЕ НИЧЕГО (ни `listing_intent`, ни
  `listing_currencies_*`).
- Buy order: `.../tradeoffer/new/?partner=<id>&token=<token>` — только
  партнёр и токен, вообще без единого параметра backpack.tf.

Это подтвердило догадку: `for_item` кладёт в ссылку САМ backpack.tf (для
объявлений на продажу — у покупки, как видно выше, вообще нет НИКАКИХ
параметров, ссылка неотличима от обычной "написать этому пользователю"), а
`listing_intent`/`listing_currencies_*` в оригинале Steam Trade Offer
Enhancer добавляет ОТДЕЛЬНЫЙ кусок расширения — скрипт, который работает
НА СТРАНИЦЕ backpack.tf при наведении на объявление. Это работа соседнего
модуля — **`bptf-listing-trade-params`, теперь тоже реализован** (см. его
раздел ниже): он дописывает `listing_intent`/`listing_currencies_*`/
`listing_item_name` в ссылку "предложить сделку" прямо на странице
backpack.tf/next.backpack.tf, до того как пользователь по ней перейдёт.
Кнопка "Добавить цену объявления" в `auto-fill-from-listing` теперь должна
появляться и для продажи, и для покупки — это ещё предстоит перепроверить
живым тестом уже с обоими модулями включёнными.

**ИСПРАВЛЕННЫЙ БАГ (баг-репорт живым тестом: в buy orders валюта партнёра
добавлялась "через раз" — иногда срабатывало, иногда нет, без видимой
закономерности).** Раньше `satisfied` в `addListingPrice` вычислялся из
того, НАШЛИСЬ ЛИ вообще DOM-элементы нужных предметов (`findKeys`/
`getItemsForMetalByScrap` ищут по данным инвентаря `g_rgPartnerAppContextData`
и проверяют только, что `document.getElementById(...)` не вернул `null`) —
но найденный элемент ещё не значит, что Steam уже успел повесить на него
`rgItem` (см. `addItemsByElements` в `utils/trade-offer.ts` — если
`elItem.rgItem` не готов, элемент молча пропускается, ничего не
добавляется). Для СВОЕГО инвентаря это никогда не проявлялось (он загружен
задолго до первого взаимодействия), а для инвентаря ПАРТНЁРА — вполне: наш
автоопрос реагирует на данные (`g_rgPartnerAppContextData`) сразу, как
только они появились, а сама отрисовка тайлов (простановка `rgItem`) —
отдельный, не обязательно синхронный шаг рендера Steam, между которыми есть
зазор. Раньше в этот зазор можно было попасть и получить `satisfied: true`,
хотя реально не добавилось ничего или добавилось частично — и опрос
(`pollAddPrice`) на этом останавливался, думая, что всё готово.
**Исправление**: вместо того чтобы верить "элементы нашлись — значит
добавилось", `addListingPrice` теперь проверяет РЕАЛЬНЫЙ результат — считает
текущую валюту в слотах ДО и ПОСЛЕ попытки (`getCurrentCurrency`, тот же
источник правды, что и для расчёта недостачи) и сравнивает с целью. Если
что-то не добавилось из-за этого зазора, `satisfied` теперь честно `false`,
и автоопрос просто пробует ещё раз через секунду — к тому моменту Steam
обычно уже успевает довесить `rgItem`.

**"Мой предмет не добавляется в buy order" — раньше это было ожидаемым
ограничением, теперь ЧАСТИЧНО автоматизировано.** Второй баг-репорт с живого
теста поднял этот вопрос: у объявления на покупку backpack.tf в принципе не
выдаёт `for_item` (нет одного конкретного ассета: покупатель готов взять
любой подходящий экземпляр, выбор — за продавцом, см.
`utils/listing-intent.ts`), поэтому auto-fill-from-listing раньше физически
не мог знать, какой именно предмет из инвентаря пользователя предложить.

По прямому запросу пользователя ("хочу, чтобы автозаполнение пыталось само
подобрать мой предмет по названию, но только если совпадение однозначное")
добавлена функция `findOwnItemByName` (core.ts): для объявлений на покупку
она ищет в СВОЁМ инвентаре предметы с именем `listing_item_name` (пишет
`bptf-listing-trade-params`, до сих пор не читалось никем) и добавляет
найденное, ТОЛЬКО если совпадение однозначное. Название (`market_hash_name`)
— не уникальный идентификатор: у одноимённых предметов могут различаться
качество, killstreak-тир, spell'ы, износ — это разные по ценности вещи.
Поэтому при НЕСКОЛЬКИХ подходящих предметах в инвентаре функция сознательно
НИЧЕГО не трогает и показывает сообщение — выбор остаётся за пользователем
(например, кнопкой "Добавить" из `quick-add-items`), как и раньше. Так же и
если подходящих предметов нет вовсе — сообщение, а не молчание. Это часть
тумблера `auto-fill-from-listing` (без клика), отдельной кнопки для этого
нет — пользователь явно попросил именно автоматику с защитой от
неоднозначности, а не ручной путь.

**Честно про статус.** Все три описанные выше правки (детект "мёртвого"
предмета, идемпотентная проверка добавленной валюты по факту, а не по
найденным элементам, и новый автовыбор своего предмета по имени для покупки)
— код-ревьюнуты и типизированы, но ещё НЕ переподтверждены свежим живым
тестом. Особенно стоит перепроверить: однозначное/неоднозначное/отсутствующее
совпадение по имени (все три ветки `findOwnItemByName`), поведение при ОБОИХ
тумблерах включённых одновременно, и распознавание объявлений на покупку
целиком (нужен `bptf-listing-trade-params`, подтверждён отдельно, но именно
в связке с новыми правками — ещё нет).

**Про `bptf-one-click-offer` (в итоге не реализован и убран из реестра).**
На момент реализации `auto-fill-from-listing` пользователь спросил, не
дублирует ли этот модуль только что сделанную работу — исследование
показало, что нет: `bptf-one-click-offer` портируется из другого проекта
(Franciscoborges2002/tf2TradingUtils), работает ТОЛЬКО с объявлениями
BOT-бейджа, использует отдельное пространство параметров (`tf2u_*`, не
`listing_*`) и, что важнее всего, сам ОТПРАВЛЯЕТ трейд-оффер прямым POST
на `steamcommunity.com/tradeoffer/new/send` — без ручного нажатия
"Отправить" (единственная защита — мобильное подтверждение Steam, если
оно вообще требуется). Это категорически более рискованное, необратимое
действие по сравнению со всем остальным в проекте (везде человек сам жмёт
финальную кнопку отправки). Тогда пользователь попросил пока его не
делать («его вообще не нужно добавлять сейчас»), а позже, при чистке
настроек, подтвердил решение окончательно и попросил убрать модуль из
реестра совсем, вместе с остальными 9 функциями (см. «Функции, которые
решено не реализовывать» ниже) — риск, описанный выше, и стал главной
причиной этого решения именно для `bptf-one-click-offer`.

### Модуль `bptf-listing-trade-params` (готовый)

Дописывает в кнопку "предложить сделку" на объявлениях backpack.tf то, чего
там самого по себе нет (см. §"Модуль `auto-fill-from-listing`" выше,
подтверждено живыми ссылками пользователя): `listing_intent`,
`listing_currencies_keys`/`listing_currencies_metal`, `listing_item_name`.
Портировано из **tf2trader** (offish/tf2-trader на GitHub,
`utils/backpack.ts#processListings`) — НЕ из Steam Trade Offer Enhancer, в
отличие от остальных модулей страницы оффера: у juliarose-форка есть только
разбор старой (не-React) вёрстки classifieds, а у tf2trader — сразу оба
слоя разметки backpack.tf, старый и новый (см. ниже).

**Первый модуль вообще без MAIN-мира.** Всё, что модуль читает и меняет —
обычный DOM самой страницы backpack.tf (текст, `data-*`-атрибуты объявления,
`href` кнопки) — никаких JS-объектов страницы, видимых только тому же
JS-реалму (как `elItem.rgItem`/`g_rgCurrentTradeStatus` на странице оффера
Steam), тут просто нет. Поэтому не нужен ни `world: 'MAIN'`, ни
`utils/bridge.ts` — весь модуль умещается в один файл (`core.ts`),
исполняющийся как обычный content-script, без пары entrypoint'ов, как у
остальных модулей.

**Два слоя разметки backpack.tf.** У backpack.tf есть классическая
(server-rendered, `data-listing_intent`/`data-listing_price` прямо на
`.item`) и "next" React-вёрстка (`next.backpack.tf`, CSS-классы вроде
`.listing__details__header`, цена — текст внутри `.item__price` с иконкой,
которую нужно вырезать перед чтением) — тот же повод, что и у
`market-item-attributes` с бета-режимом Steam Market (см. выше). Различаются
только `parseLegacyListing`/`parseNextListing` — какой из них применить,
решается один раз по хосту страницы (`next.backpack.tf` целиком на React,
обычный `backpack.tf` — целиком нет, смешения не бывает).

**`for_item` для продажи — только ДОБАВЛЯЕМ, если backpack.tf его ещё не
положил, никогда не перезаписываем.** Живой тест (см. выше) подтвердил, что
native-ссылка backpack.tf для объявления на продажу УЖЕ несёт корректный
`for_item` сама — трогать готовое правильное значение своим (пусть даже
вычисленным тем же способом, что в tf2trader — из href самой карточки
объявления в "next"-режиме) было бы лишним риском разойтись с оригиналом
без всякой пользы.

**`listing_item_name`** — имя предмета объявления, нужно ГЛАВНЫМ ОБРАЗОМ для
объявлений на ПОКУПКУ, у которых нет `for_item` (нет одного конкретного
ассета — см. `utils/listing-intent.ts`). Пишется уже сейчас, но
`auto-fill-from-listing` пока его не читает — см. его раздел выше за тем,
почему это отдельная, более осторожная задача (поиск по имени не даёт
однозначный assetId, в отличие от `for_item`).

**MutationObserver на весь `document.body`, а не только "next"-режим.**
Оригинал в tf2trader ставит наблюдатель только на `next.backpack.tf` и
`backpack.tf/stats` (там объявления подгружаются без перезагрузки страницы),
а на классических `backpack.tf/classifieds` — только один проход при
загрузке (там пагинация — обычная перезагрузка страницы). Здесь наблюдатель
стоит везде одинаково: он безвреден там, где не нужен (обработанные
объявления помечаются `data-tf2s-listing-params`, повторный проход по ним —
дешёвый no-op), а не заводить два разных пути ради этого различия показалось
более простым и меньше похожим на источник будущего бага, чем экономия
одного наблюдателя.

**Честно про статус.** Не проверялся на живом backpack.tf — реализация
портирована из tf2trader (тот же самый паттерн, который эта команда уже
использует в собственном похожем расширении), но верстка backpack.tf могла
измениться. Стоит проверить: и классические `backpack.tf/classifieds`, и
`next.backpack.tf/classifieds`, и `backpack.tf/stats/*` — что после
перехода по кнопке "предложить сделку" в адресной строке появились
`listing_intent`/`listing_currencies_*` (сравнить с тем, что показывали
ссылки без этого модуля — см. §"Модуль `auto-fill-from-listing`" выше), и
что кнопка "Добавить цену объявления" там же на странице оффера теперь
появляется.

### Модуль `offer-currency-total` (готовый)

Первый модуль на странице **списка офферов** (`steamOffersList` в реестре —
`/tradeoffers`, `/tradeoffers/sent`, `/tradehistory`), до этого у неё вообще
не было ни одной готовой функции. Показывает двухколоночную плашку валюты
для каждой записи списка/истории — что каждая сторона отдаёт/получает,
одним взглядом, не открывая сам оффер. Портировано из **tf2TradingUtils**
(Franciscoborges2002/tf2TradingUtils,
`steamcommunity.com/tradeOfferCurrency/content.js#addTradeCurrencyTotals`).

**Не то же самое, что `trade-item-summary` (тот же принцип, другая
страница).** `trade-item-summary` уже делает похожую сводку по сторонам —
но НА СТРАНИЦЕ ОФФЕРА, читая `window.g_rgCurrentTradeStatus`. Здесь того же
JS-глобала просто нет — список офферов/история не отдают ничего специфичного
для JS-реалма страницы (как и `bptf-listing-trade-params` — второй модуль
вообще без MAIN-мира, весь код в одном ISOLATED `core.ts`). Поэтому общего
кода с `trade-item-summary` тут по факту нет — переиспользуется только
форматирование суммы (`utils/currency.ts#formatKeysAndScrap`, новая
маленькая функция рядом с уже существующим `formatMetalScrap`, требование 4).

**Две РАЗНЫЕ разметки → два разных способа узнать валюту предмета.**
- `/tradeoffers`(`/sent`): строка — `.tradeoffer`, у каждого предмета
  (`.trade_item`) нет вообще никакого имени/текста — только иконка и
  `data-economy-item="classinfo/440/<classid>/<instanceid>"`. Валюта
  матчится по `classid` — это Steam-economy id, ОТДЕЛЬНЫЙ от TF2-схемного
  `defindex` из `utils/currency.ts` (см. её комментарий) — те самые четыре
  значения, что tf2TradingUtils подтвердил живыми classinfo-ответами. Плюс
  резервный путь по хэшу иконки в `src`, на случай если `data-economy-item`
  у какого-то аккаунта/локали вдруг не окажется — это уже НЕ проверено
  живым тестом, чистая подстраховка на основе того же портирования.
- `/tradehistory`: строка — `.tradehistoryrow`, у каждого предмета
  (`.history_item`) ЕСТЬ обычное имя (`.history_item_name`) — здесь
  достаточно уже существующего `getCurrencyKindFromName`, отдельный
  classid-путь не нужен вовсе.

**Подсчёт количества читает бейдж "×N" от `offer-item-summary`.** У
оригинала (tf2TradingUtils) это чтение бейджа своей же компаньон-фичи
(`groupTradeItems`, схлопывающей повторяющиеся предметы в один тайл +
бейдж с числом) — здесь то же самое, только координация между двумя
независимыми content-скриптами явная: `utils/offer-list-badges.ts`
экспортирует имена классов (`tf2s-item-qty`/`tf2s-history-qty`) и
`getBadgeQty(el, badgeClass)`, который берёт число из бейджа, если он уже
есть, и безопасно возвращает `1`, если `offer-item-summary` выключен или
ещё не успел отработать (порядок срабатывания двух независимых
`MutationObserver` не гарантирован, поэтому `getBadgeQty` — единственный
контракт между модулями, никаких предположений о том, кто выполнится
первым). `sumOfferSide`/`sumHistorySide` теперь умножают `keys`/
`metalScrap`/`itemCount` на это число вместо `+= 1`. Для `/tradehistory`
есть отдельный нюанс: `offer-item-summary` дописывает бейдж прямо ВНУТРЬ
`.history_item_name`, так что при чтении имени предмета для
`getCurrencyKindFromName` он предварительно вырезается через новый
`cloneWithoutBadge` — иначе текст бейджа ("×5") попадёт в матчинг имени и
сломает его.

**MutationObserver, а не разовый проход — сознательное отличие от
оригинала.** tf2TradingUtils сканирует ровно один раз при загрузке страницы,
без учёта того, что Steam догружает историю (и, реже, список) постранично
AJAX-кнопкой "Load More" без полной перезагрузки — на новые строки оригинал
уже не среагирует. Здесь тот же debounce-паттерн, что и у
`bptf-listing-trade-params`: обработанные строки помечаются
`data-tf2s-currency-total`, повторный проход по ним — дешёвый no-op, так что
держать наблюдатель "на всякий случай" ничего не стоит.

**ИСПРАВЛЕНО (первый живой тест: плашка не появлялась вообще ни у одной из
12 входящих офферов).** Диагностика через консоль браузера (пошагово: число
`.tradeoffer`-строк → `data-tf2s-currency-total` на них → число
`.tf2s-offercur`-плашек → результат `.tradeoffer_header`/`.tradeoffer_items`-
селекторов → сырые `data-economy-item` каждого предмета) показала, что
`.tradeoffer_header`/`.tradeoffer_items_ctn > .tradeoffer_items`/
`data-economy-item` — ВСЕ угаданы верно, скрипт честно доходил до отрисовки
на всех 12 строках. Плашка не появлялась, потому что ни у одной из этих 12
входящих офферов не было ни ключей, ни металла ни с одной стороны — только
предметы (в одной из строк даже нашёлся classid, подозрительно похожий на
ключ из-за общего префикса "101785", но пользователь опознал предмет как
"Mann Co. ticket", не ключ — совпадение первых цифр, не связанные предметы).
А `renderTotalBox` в изначальном порте (как и в оригинале tf2TradingUtils)
сознательно ничего не рисовал, если валюты нет НИ У ОДНОЙ стороны — "трейд
без валюты вообще не для этой плашки". Пользователь явно попросил другое:
плашка должна быть ВСЕГДА, показывая число предметов вместо суммы, когда
валюты нет — то есть самый частый на практике случай (чисто предметные
офферы) не должен оставлять пользователя гадать, работает ли модуль вообще.
Исправлено — `renderTotalBox` больше не возвращает `null` из-за отсутствия
валюты, только если сторон вообще нет.

**Честно про статус.** classid-таблица (`/tradeoffers`,`/tradeoffers/sent`)
и селекторы `.tradeoffer_header`/`.tradeoffer_items_ctn`/`.trade_item`/
`data-economy-item` подтверждены живым тестом (см. выше) — но ТОЛЬКО для
предметов без валюты (среди тестовых офферов ключей/металла не нашлось).
Сам classid-матчинг валюты (`CURRENCY_KIND_BY_CLASSID`) и резервный путь по
хэшу иконки (`CURRENCY_KIND_BY_ICON_HASH`) — до сих пор НЕ подтверждены
живым тестом на реальном ключе/металле; более того, найденный в этом же
тесте формат картинки (`.../economy/image/class/440/<classid>/<size>`, БЕЗ
хэша в URL вообще) ставит под сомнение, работает ли резервный путь по хэшу
в принципе на современном Steam CDN — нужно перепроверить на офере, где
валюта точно есть. `/tradehistory` (имя предмета вместо classid) и
поведение MutationObserver на реальной AJAX-подгрузке истории — тоже ещё не
проверены вживую. Ниже описанное чтение бейджа `offer-item-summary`
(количество вместо честной "1 предмет = 1 тайл") — тоже пока НЕ проверено
живым тестом: ни на одном из 12 тестовых офферов повторяющихся предметов
не встретилось.

### Модуль `offer-item-summary` (готовый)

Второй модуль страницы **списка офферов** (`steamOffersList`), напарник
`offer-currency-total` — схлопывает несколько одинаковых предметов в один
тайл с бейджем "×N" вместо N визуально одинаковых иконок подряд.
Портировано из **tf2TradingUtils**
(`steamcommunity.com/groupTradeItems/content.js`).

**Тот же принцип, что и `offer-currency-total`, только запись, а не
чтение.** Обе фичи независимы (каждая — свой `status` в реестре, свой
тумблер в опциях, требование 4), обе смотрят на одни и те же 6 URL-паттернов
(`/tradeoffers`, `/tradeoffers/sent`, `/tradehistory`, все три в вариантах
`/id/*`, `/profiles/*`, `/my/*`), но если включена только эта — просто
получаешь схлопнутые тайлы без плашки валюты, и наоборот. Координация между
ними — не порядок выполнения (гарантий тут нет, у каждой свой независимый
`MutationObserver`), а общий контракт через `utils/offer-list-badges.ts`:
эта фича ПИШЕТ бейдж, `offer-currency-total` его ЧИТАЕТ через `getBadgeQty`
(см. предыдущий раздел).

**Две те же разные разметки, что и у `offer-currency-total` → два разных
способа группировки.**
- `/tradeoffers`(`/sent`): предметы группируются по значению атрибута
  `data-economy-item` (тот же classid+instanceid, что использует
  `offer-currency-total` для матчинга валюты — тут просто ключ группировки,
  без интерпретации). Из группы оставляется первый элемент, остальные
  удаляются из DOM целиком (`.remove()`), на оставшийся навешивается
  `position: relative` (для абсолютно спозиционированного бейджа в углу
  иконки, `.tf2s-item-qty`) и добавляется `<span>` с текстом `×N`.
- `/tradehistory`: группировка по тексту `.history_item_name` (здесь, как и
  у `offer-currency-total`, никакого `data-economy-item`-эквивалента для
  истории нет — только имя). Оставшиеся лишние `.history_item` тоже
  удаляются, но здесь ещё нужно чистить осиротевший разделитель-запятую
  между именами (`removeWithSeparator` — Steam разделяет имена в списке
  текстовым узлом `", "` между элементами, без него после удаления соседних
  элементов остаётся висячая запятая); бейдж `.tf2s-history-qty` дописывается
  инлайново внутрь `.history_item_name` (не абсолютным позиционированием,
  как на списке офферов — тут это просто ещё один инлайн-элемент рядом с
  текстом имени).

**Почему `offer-currency-total` не может просто посчитать
`.trade_item`/`.history_item` сама, без этой фичи.** Могла бы — до
схлопывания. Но эта фича физически удаляет лишние DOM-элементы (не прячет
через CSS), так что после её работы посчитать что-либо, кроме "1 видимый
тайл = 1 предмет", уже нельзя без бейджа — отсюда и общий контракт,
описанный выше, а не что-то более случайное вроде подсчёта по количеству
элементов до/после.

**MutationObserver + debounce + идемпотентность — тот же паттерн, что и у
всех остальных модулей этой страницы** (`bptf-listing-trade-params`,
`offer-currency-total`): группы помечаются `data-tf2s-grouped`, повторный
проход по уже обработанной группе — no-op, так что AJAX-подгрузка
(`/tradehistory`'s "Load More" и, реже, `/tradeoffers`) не требует ничего
особенного.

**Живым тестом подтверждена сама механика группировки на `/tradeoffers`.**
На реальном оффере с 149 предметами (крупный "мусорный" трейд) группировка
по `data-economy-item` сработала корректно для настоящих дублей — например,
одинаковые тикеты Mann Co. (`101785317/11040578`) в двух разных офферах
корректно схлопнулись в тайлы `×4` и `×2`. Визуальное позиционирование
бейджа `.tf2s-item-qty` (`position: relative` на тайле + `absolute` бейдж
поверх иконки) тоже подтверждено — не наезжает на соседние элементы.
`/tradehistory` (группировка по имени + чистка запятой-разделителя) и
поведение MutationObserver на AJAX-подгрузке истории — всё ещё НЕ проверены
живым тестом.

**ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ (подтверждено живым тестом, не планируется
чинить сейчас — по явному решению пользователя).** Предметы, отличающиеся
ТОЛЬКО косметической надписью "Level N" (случайное число у обычного/не
Strange/не Unusual оружия TF2, не влияет ни на статы, ни на цену), НЕ
склеиваются в один тайл, хотя по ценности это один и тот же предмет —
пользователь live-тестом нашёл несколько "The Thermal Thruster" разных
уровней (87/94/90/48/18 и т.д.), визуально неотличимых, но с разным
`classid` в каждом. Причина: у Steam разный текст описания = разный
`classid` (эта строка "Level N" — часть classid-scoped описания, а не
instanceid-scoped атрибута), и в самой разметке `.trade_item` НЕТ ни имени,
ни качества текстом — только `data-economy-item` и `<img src>` (проверено
через `outerHTML` живых элементов); настоящее имя/качество Steam подгружает
отдельным запросом только по наведению мыши (та самая всплывающая
подсказка), в исходном HTML при загрузке страницы этого нет. Чтобы
склеивать такие предметы правильно (по имени+качеству, игнорируя Level),
нужно было бы либо группировать по `<img src>` (просто, но тогда Strange/
Vintage/обычный вариант одного оружия с одинаковой иконкой тоже склеятся,
хотя стоят по-разному), либо тянуть реальное имя через
`/economy/itemclasshover/...` для каждого уникального предмета (точнее, но
лишние сетевые запросы на офферах с кучей разных предметов, риск упереться
в рейт-лимит Steam). Это ограничение унаследовано от самого порта — у
оригинала tf2TradingUtils (`groupTradeItems`) group-ключ тот же самый,
буквальный `data-economy-item`, так что там та же самая проблема.

### Модуль `stn-item-links` (готовый)

Первый модуль для **stntrading.eu** (`stnTrading` в реестре — до этого ни
одной готовой функции). Одна кнопка-ссылка "Проверить на PriceDB.io" на
странице конкретного предмета (`stntrading.eu/item/tf2/<имя>`). Портировано
из **tf2TradingUtils** (`stntrading.eu/itemLinks/content.js`), но сильно
УПРОЩЕНО по сравнению с оригиналом — см. ниже, почему.

**Почему не пять ссылок, как в изначальном описании реестра.** У
оригинала `itemLinks` строит ссылки на bp.tf/mannco.store/marketplace.tf/
Steam Market/Wiki самостоятельно — ради чего с собой тащит `~180Кб`
вшитого JSON (`utils/data/tf2ItemDefindexes.json`, полная TF2-схема
"имя → defindex") и резолвер поверх него (`utils/tf2ItemSchema.js`), просто
чтобы построить marketplace.tf/pricedb.io-style "sku"
(`defindex;quality;модификаторы`). В процессе реализации выяснилось, что
у нас в проекте УЖЕ есть свой резолвер ровно того же самого sku — PriceDB.io
(`utils/pricedb.ts#resolveSku`, тот же провайдер, что и в
`pricedb-check-button`/`market-pricedb-check-button`, requirement 4) — и
страница конкретного предмета на PriceDB.io САМА ссылается на добрый
десяток других площадок разом, включая Steam Market (подтверждено живым
запросом WebFetch на `pricedb.io/item/143;6` — Backpack.tf, Backpack.tf
Next, STN Trading, Mannco.store, Skinport, Merchant.tf, CTrade.tf, Steam
Community Market, Gladiator.tf; marketplace.tf среди них не оказалось, но
остальные из изначального списка покрыты и с запасом). Идею — сделать
ставку на один агрегатор вместо пяти отдельных ссылок — предложил
пользователь по ходу обсуждения; он же затем попросил убрать и
самодельную ссылку на Steam Market, которая изначально была ЕЩЁ отдельной
кнопкой (строила URL напрямую из текста `<h1>`, без резолва) — раз
PriceDB.io и так ссылается на Steam Market, но уже ИЗ РЕЗОЛВНУТОГО SKU, то
есть гарантированно на правильный предмет любого качества, а не только
для тех случаев, когда сырой текст `<h1>` совпадает с реальным
market_hash_name. Итог — ровно одна кнопка. Wiki и marketplace.tf так и
не строим отдельно: Wiki ссылается на статью БАЗОВОГО предмета без учёта
качества (потребовал бы ту же операцию "срезать слово качества из
имени", которой сейчас нигде в проекте нет), а marketplace.tf недостижим
без той же самой TF2-схемы, которую мы решили не тащить.

**Разметка и место вставки — с реального аккаунта пользователя.** WebFetch
не годится для этой страницы напрямую (прогоняет HTML через
markdown-конвертацию, конкретные классы/структуру не разглядеть) —
пользователь прислал сырой `view-source:` HTML целиком
(`stntrading.eu/item/tf2/Taunt%3A+The+High+Five%21` со своего аккаунта).
Название предмета — в `<h1 class="fs-3 card-title">` (полное, с префиксом
качества/Non-Craftable, как Steam market_hash_name — подтверждено живым
HTML: "Taunt: The High Five!" для Unique без префикса, "Unusual Taunt: The
High Five!"/"Non-Craftable Taunt: The High Five!" с префиксом — та же
схема именования, что уже использует `utils/pricedb.ts`). Кнопка
вставляется не рядом с `<h1>` (их на странице ДВА — mobile/desktop
responsive-дубликаты одного и того же текста, `d-block d-sm-none` и
`d-none d-sm-block`), а рядом с `#request_reprice` ("Request Repricing") —
их же собственной кнопкой той же природы ("узнать больше про предмет"),
которая на странице ОДНА (не дублируется под mobile/desktop). Оформлена
ИХ ЖЕ bootstrap-классами (`btn btn-secondary rounded-0` + их же
`ms-2`/`my-1` утилиты отступов) — по прямой просьбе пользователя
("стилизовать под дизайн STN") вместо своей палитры цветов, как у соседних
plain-DOM модулей (`offer-currency-total`/`offer-item-summary`): здесь так
было бы неверно, чужая страница уже целиком оформлена своим Bootstrap 5,
своя палитра выглядела бы инородно рядом с их родными кнопками. Резервный
путь на случай отсутствия `#request_reprice` у какого-то типа страницы
(не проверено живым тестом на каждом типе предмета) — вставка после
КАЖДОГО `<h1 class="card-title">`, тем же приёмом, что раньше был
основным.

**MutationObserver — на случай SPA-навигации между предметами.** Не
проверено живым тестом, переключается ли stntrading.eu между страницами
предметов ("You may also like"/"Other Taunts" внизу своей же страницы)
через полную перезагрузку или через клиентский роутинг без неё — сайт
активно использует `data-event-binding`-обвязку поверх обычных `<a>`, так
что второе не исключено. На случай второго — тот же debounce-паттерн, что
у всех остальных модулей `steamOffersList`, `PROCESSED_ATTR` для
идемпотентности (на `#request_reprice` в основном пути, на каждом `<h1>`
в резервном).

**Честно про статус — не проверено живым тестом.** Сама разметка
(`h1.card-title`, `#request_reprice`) подтверждена прямым просмотром
живого HTML — но клик по самой кнопке, вид на реальной (не Unique)
странице — Unusual/Strange/Non-Craftable предмете — и поведение
SPA-навигации между предметами ещё не проверены. Как и у
`market-pricedb-check-button` — резолв SKU для Unusual-предметов не
делает специальной обработки имени эффекта (не вырезает слово "Unusual" и
не подставляет имя эффекта отдельно, как это делает
`pricedb.ts#buildPriceableName` для трейд-офферов — там имя эффекта
берётся из уже распарсенных атрибутов Steam classinfo, которых на этой
странице просто нет) — если PriceDB.io не сможет распознать Unusual по
такому имени, ссылка тихо откатится на страницу поиска
(`pricedbSearchUrl`) вместо точной страницы предмета — то же самое
осознанное упрощение, что уже принято в `market-pricedb-check-button`.

### Модуль `inventory-currency-counter` (готовый)

**Не путать с `wallet-summary`**: `wallet-summary` — плавающее окно в
окне трейд-оффера, считает ОБЕ стороны сразу (вы + партнёр). Этот
модуль — панель на странице **вашего собственного инвентаря**
(`steamcommunity.com/id|profiles/<x>/inventory`), одна сторона, и
**явно НЕ плавающее окно**: по прямому требованию — «не окно поверх
вкладки, а информация, встроенная в дизайн Steam-инвентаря» — панель
вставляется прямо в разметку страницы сразу под панелью фильтров
инвентаря (`.filter_ctn.inventory_filters`) и оформлена как её
собственный блок (`position: static`, без хоста `position: fixed`,
без ручки перетаскивания — сравните `panel.css` этого модуля и
`modules/wallet-summary/panel.css`).

- `utils/inventory-watch.ts` — перехват `window.fetch`/`XMLHttpRequest`
  за постраничными запросами страницы инвентаря
  (`/inventory/<id>/440/2`), вынесенный из `inventory-item-attributes`
  в общий файл (требование 4): оба модуля хотят знать, какие предметы
  Steam уже показал на вкладке, просто по-разному их используют
  (значки атрибутов vs подсчёт валюты). Синглтон держится на
  `window.__tf2suiteInventoryWatch`, а не на module-level переменной —
  `inventory-item-attributes` и `inventory-currency-counter` это ДВА
  разных content-скрипта, WXT собирает каждый в свой отдельный бандл со
  своим module-scope, и обычный `let installed = false` в двух бандлах
  не увидел бы друг друга (оба патчили бы `fetch`/XHR независимо).
  `window` — единственное состояние, реально общее для любого числа
  MAIN-world скриптов на одной странице.
- `modules/inventory-currency-counter/core.ts` — два источника данных:
  быстрая **бесплатная** оценка (0 доп. запросов) по уже накопленной
  `installInventoryWatch()`-карте, и точный подсчёт по кнопке
  "Обновить" (`forceFullFetch: true`) — переиспользует
  `utils/inventory-fetch.ts#fetchCurrencyWallet` (тот же путь, что и
  `wallet-summary`). SteamID64 владельца инвентаря берётся из id
  DOM-контейнера сетки TF2 (`inventory_<steamid64>_440_2`), а НЕ из
  `link[rel="canonical"]` — живой проверкой подтверждено, что этого тега
  нет на vanity-URL страницах (`/id/<name>/`), хотя именно на него
  ссылается справочный проект.
- `modules/inventory-currency-counter/panel.ts` + `panel.css` —
  встроенная горизонтальная полоска чипов (Keys/Ref/Rec/Scrap + итог в
  ref), фоново пересчитывается каждые 2 с (бесплатно, без сети, пока
  видима), кнопка `⟳` запускает точный полный фетч. Подпись показывает
  либо «~ показано X из Y» (частичная оценка), либо «точно · N предм.»
  (после полного фетча).
- `entrypoints/inventory-currency-core.content.ts` — MAIN world,
  `runAt: 'document_start'` (тот же баг с таймингом, что чинили в
  `inventory-item-attributes` — перехват должен встать раньше первого
  собственного запроса страницы).
- `entrypoints/inventory-currency.content.ts` — ISOLATED world, ручное
  (не автомонтирование WXT) управление `mount()`/`remove()`: панель
  показывается только когда активна именно вкладка TF2 (`location.hash
  === '#440'`, с фолбэком на видимость самого контейнера
  `inventory_<id>_440_2`, если хэш пуст — на первой загрузке страницы
  хэш может быть пустым даже при уже показанной по умолчанию вкладке).
  Синхронизация — по `hashchange`, debounced `MutationObserver` на
  `#tabcontent_inventory` и несколько отложенных проверок (0/600/1500/
  3000 мс) на случай, если Steam ещё дорисовывает вкладки.

### Модуль `trade-item-summary` (готовый)

**Не путать ни с `wallet-summary`, ни со старым описанием этого id в
реестре** (изначально `trade-item-summary` был зарегистрирован как «группировка
предметов в слотах с бейджем количества + клик открывает backpack.tf» — это
ДРУГАЯ, ещё не реализованная идея; при обсуждении пользователь переопределил
этот модуль под конкретную задачу ниже, `title`/`description` в
`utils/registry.ts` обновлены соответственно). `wallet-summary` считает ВЕСЬ
инвентарь обеих сторон (не только предложенное); этот модуль считает **только
то, что реально лежит в слотах оффера прямо сейчас**, по требованию
пользователя. Валюта (keys/ref/rec/scrap) считается всегда; остальные
предметы — по выбору в настройках, просто число ИЛИ их суммарная оценка по
PriceDB.io (см. ниже). Блок явно **не плавающий** и **не общий
на двух сторон** — два независимых экземпляра, каждый встроен в разметку
своей стороны сразу под `.offerheader` (аватар + имя), перед `.trade_item_box`
(подтверждено структурой реальной сохранённой страницы оффера, которую
прислал пользователь).

- `modules/trade-item-summary/core.ts` — MAIN world, источник данных
  **не DOM**, а `window.g_rgCurrentTradeStatus` — тот же объект, что Steam сам
  живьём мутирует по мере перетаскивания предметов в/из слотов
  (`{me:{assets:[...]}, them:{assets:[...]}}`, каждый asset — только
  `{appid, contextid, assetid, amount}`, без имени). Имя для определения
  валюты (`utils/currency.ts#getCurrencyKindFromName`) берётся из уже
  загруженного Steam'ом полного инвентаря обеих сторон
  (`window.g_rgAppContextData` / `g_rgPartnerAppContextData` — те же
  глобали, что использует `trade-item-attributes`) по `assetId`. Читается
  каждый раз заново по запросу (не кэшируется при регистрации обработчика),
  поэтому всегда видит актуальное состояние оффера. Предметы не из 440/2
  (Steam разрешает добавлять в оффер вещи из других игр одновременно)
  отфильтровываются.
- `modules/trade-item-summary/panel.ts` + `panel.css` — встроенная (не
  плавающая, `position: static`) полоска чипов: ключи — отдельным числом,
  металл (ref+rec+scrap) — одной суммой в ref через
  `metalValueInScrap`/`formatMetalScrap` из `utils/currency.ts` (по
  требованию пользователя ключи **не** сворачиваются в общий ref-эквивалент,
  в отличие от `wallet-summary`). Пересчёт — по `MutationObserver` на
  `#your_slots`/`#their_slots` этой стороны (Steam обновляет DOM слотов и
  `g_rgCurrentTradeStatus` синхронно в одном обработчике drag&drop, так что
  мутация DOM — надёжный и мгновенный триггер), плюс лёгкий поллинг раз в 2 с
  как подстраховка (0 доп. запросов на саму валюту — MAIN просто читает уже
  готовый объект).
- **БАГ (исправлено): округление металла в ref.** Раньше `formatMetalScrap`
  округляло математически (`Math.round`) — 2 Reclaimed (6 scrap) показывались
  как "0.67 ref" вместо ожидаемых "0.66 ref" (заметил пользователь). В
  TF2-трейдинге стоимость металла в ref принято ОКРУГЛЯТЬ ВНИЗ (усечение) —
  каждый scrap добавляет ровно 0.11 ref по нарастающей (1 -> 0.11, 2 -> 0.22,
  ..., 9 -> 1.00), округление вверх/к ближайшему может визуально завысить
  сумму относительно того, что реально лежит в оффере/инвентаре. Исправлено
  в одном общем месте — `utils/currency.ts#truncateDecimal2` (усечение до 2
  знаков, `Math.floor`, не привязано к делению на 9 — им же пользуется и
  режим 'priced' ниже для цен PriceDB.io, которые уже приходят в ref/keys
  без промежуточного scrap). Затронуло ВСЕ модули, показывающие металл в ref
  (`wallet-summary`, `inventory-currency-counter`, `trade-item-summary`) —
  общая функция, один фикс на всех (требование 4).
- **Режим работы с НЕ-валютными предметами — выбор в настройках модуля**
  (по предложению пользователя): `utils/trade-summary-mode.ts`
  (`TradeSummaryMode = 'simple' | 'priced'`, хранится в `moduleOptions`
  модуля — тот же паттерн, что и `IconDetailLevel` у `trade-item-attributes`,
  переключатель в `components/FeatureToggle.vue`). Валюта считается ОДИНАКОВО
  в обоих режимах — режим влияет только на "прочие" предметы:
  - **`simple`** (по умолчанию) — просто число штук, без цены, без сети.
  - **`priced`** — плюс их суммарная оценка по [PriceDB.io](https://pricedb.io)
    (публичный агрегатор цен TF2, без ключа) — отдельно в keys и в ref (та же
    логика "ключи не сворачиваются в ref", что и у самой валюты оффера).
    Реализация — `utils/pricedb.ts`, общий файл (им же пользуются
    `pricedb-check-button` и `market-pricedb-check-button`, тот же провайдер
    цен, требование 4 — см. их описание ниже):
    - `buildPriceableName(item, attrs)` — строит имя для их SKU-резолвера
      (`GET sku.pricedb.io/api/name/<имя>`). Для большинства предметов это
      просто `market_hash_name` как есть (подтверждено живыми запросами:
      "Strange Professional Killstreak Backburner" и "Australium Rocket
      Launcher" резолвятся напрямую). **Исключение — Unusual**: Steam не
      кладёt название эффекта в `market_hash_name` (только "Unusual
      <предмет>"), а резолвер, наоборот, ожидает "<Effect Name> <предмет>"
      БЕЗ слова "Unusual" (подтверждено: "Unusual Team Captain" ->
      `effect: null`, а "Burning Flames Team Captain" -> `effect: 13`, sku
      `378;5;u13`) — поэтому для предметов с найденным effect (уже считает
      `getItemAttributes`) вырезаем "Unusual " и подставляем имя эффекта из
      `utils/unusual-effects.ts#getEffectName` (новая обратная карта
      id -> имя, к уже существовавшей `getEffectId`).
    - Цена берётся `GET pricedb.io/api/item/<sku>` (после резолва SKU),
      поле `sell` ("во что оценивается предмет"). SKU и цена кэшируются в
      модульном `Map` на время жизни вкладки — повторные опросы (раз в 2 с)
      не бьют по сети повторно за уже виденные предметы.
    - **Важно про CORS**: сетевые вызовы `utils/pricedb.ts` зовутся ИЗ
      ISOLATED-стороны (`panel.ts`), а НЕ из MAIN (`core.ts`) — MAIN-скрипт
      выполняется как часть самой страницы Steam и его `fetch` подчиняется
      её CORS; content-скрипту с `host_permissions` на `pricedb.io`/
      `sku.pricedb.io` (см. `wxt.config.ts`) браузер разрешает кросс-доменный
      fetch в обход CORS-ответа их сервера. MAIN (`core.ts`) готовит только
      "прайсабельные" имена (`TradeSideSummary.otherItems`) — сеть не трогает
      вообще.
    - Любая сетевая неудача (таймаут 5 с, предмет не найден, PriceDB.io
      недоступен) — предмет просто остаётся посчитан как "без цены"
      (пометка "нет цены" у его строки), без ошибок и без блокировки
      остальной панели.
    - **Построчная раскладка + ссылка-проверка на pricedb.io.** В режиме
      `priced` каждый уникальный предмет — своя строка (имя + цена за штуку,
      `×N` если их несколько одинаковых), а не одно общее число: пользователь
      явно попросил способ перепроверить, что цена подобрана к правильному
      предмету/эффекту, агрегата для этого недостаточно. У каждой строки —
      ссылка "↗", открывающая `https://pricedb.io/item/<sku>` (человеческая
      страница самого pricedb.io с их "Suggested Price", живьём проверено
      WebFetch) в новой вкладке; если SKU не зарезолвился — ссылка ведёт на
      их поиск по имени (`pricedb.io/search?q=<имя>`), чтобы можно было
      разобраться, почему предмет не нашёлся, а не просто получить тупик.
      Копия итога (сумма по всем оценённым предметам стороны) остаётся под
      списком, но только когда оценённых предметов ≥2 — иначе он дословно
      повторял бы единственную строку.
    - **Переименованные предметы (Name Tag) не путают цену.** Проверено
      живьём на Steam Market: поиск по оригинальному имени предмета
      ("Buck Turner All-Stars") находит все его лоты (в т.ч. переименованные
      экземпляры), а поиск по кастомному нику ("Adidash Running Shoes") не
      находит ничего — Steam группирует все копии предмета на Market по
      каноническому имени (`market_hash_name`), которое НЕ меняется от
      Name Tag'а (меняется только `name` — то, что видно в инвентаре).
      И `buildPriceableName` (сюда), и `getCurrencyKindFromName`
      (`utils/currency.ts`, подсчёт валюты) намеренно берут именно
      `market_hash_name`, а не `name` — 2 переименованных копии одного
      предмета в оффере корректно схлопнутся в одну строку с одной ценой
      (сгруппированы в `core.ts` по этому же имени), а не разъедутся на
      "предмет" и "неизвестно что" с разными/нулевыми ценами.

  `inventory-item-attributes`/`inventory-currency-counter` (требование 4).
- **React полностью пересобирает `innerHTML` панели при каждом клике по
  предмету** — просто вставленная один раз кнопка исчезает при следующем
  выборе. Поэтому `entrypoints/inventory-pricedb.content.ts` не монтирует
  UI один раз, а вызывает `ui.remove()`+`ui.mount()` заново при КАЖДОЙ
  смене выбранного предмета (через `createShadowRootUi` с `anchor:
  findMountTarget` — функция, не статический селектор, перевычисляется на
  каждый `mount()`, включая заново `findCardBody` внутри) — простой toggle
  видимости, как у `inventory-currency-counter`, тут не подходит.
- **Редизайн (по просьбе пользователя).** Первая версия — залитая акцентным
  оранжевым кнопка (`tf2s-btn--accent`) — визуально "кричала" рядом с
  приглушёнными родными кнопками Steam. Заменена на приглушённый
  "вторичный" чип — тонкая рамка (`var(--tf2s-border)`), тёмный фон
  (`var(--tf2s-surface-2)`), `width:100%` продолжает вертикальный стек
  группы действий; акцентный оранжевый остался только у иконки "↗" и
  целиком проявляется в hover. Между этим и финальной версией была
  промежуточная попытка визуально СЛИТЬ кнопку с родными рядами впритык
  (без рамки/фона, `padding:16px` — точь-в-точь как у самих рядов Steam,
  подсмотрено `getComputedStyle`) — пользователь попросил вернуть именно
  этот, приглушённый-но-обособленный стиль чипа, оставив только новое,
  верное МЕСТО кнопки (см. пункт выше) — не переигрывать дизайн заново на
  каждый фикс позиционирования.
- assetId выбранного предмета — не из панели (там его нет), а из самой
  плитки сетки: Steam помечает выбранную классом `.activeInfo`, а её `id` —
  готовый `"440_2_<assetId>"` (в отличие от офера, тут без префикса `item`).
- `modules/pricedb-check-button/panel.ts` — сначала показывает рабочую
  ссылку на страницу ПОИСКА PriceDB.io (мгновенно, без сети), затем
  апгрейдит её на точную страницу предмета, когда зарезолвится SKU — тот же
  приём "оптимистичная ссылка + апгрейд", что и у ссылок-проверок в
  `trade-item-summary`. `utils/pricedb.ts#resolveSku` вынесен наружу
  (экспортирован) специально для этого: нужен только SKU для ссылки, не
  сама цена — второй сетевой запрос (`fetchPrice`) был бы лишним.

### Модуль `market-pricedb-check-button` (готовый)

Тот же принцип "кнопка-проверка цены на PriceDB.io", что и у
`pricedb-check-button`, но на странице листингов Steam Market — по явной
просьбе пользователя ("я бы еще добавил для стим маркета такое же").
**Не переиспользование одной фичи на два сайта** — отдельная запись в
`utils/registry.ts` (`FeatureModule.site` — одиночное значение, не массив,
требование 1: раздельные тумблеры по сайтам) и отдельный модуль, потому что
устройство страницы принципиально другое:

- На инвентаре кнопка ОДНА (для выбранного предмета). На Market она нужна
  **у каждой строки листинга отдельно** — сам Steam Market НЕ различает
  конкретный Unusual-эффект/killstreak sheen/spell в своей собственной
  отображаемой цене: все листинги одного базового предмета на странице
  показывают одну и ту же цену, независимо от реального содержимого
  (общеизвестный факт торговли TF2, подтверждено живым просмотром страницы
  ключа/безделушки). Без построчной кнопки не было бы способа проверить
  цену именно того варианта, который заинтересовал.
- **Общий источник данных с `market-item-attributes` вынесен в
  `utils/market-item-source.ts`** (требование 4 — раньше классик/бета-ветка
  чтения `window.g_rgAssets`/`installMarketBetaWatch()` жила только внутри
  `market-item-attributes/core.ts`; теперь оба модуля читают один и тот же
  `readMarketItemSource()`, каждый со своим преобразованием — атрибуты для
  значков или priceable-имя для PriceDB.io). Той же рефакторинг перенёс
  `beta-watch.ts` из `modules/market-item-attributes/` в
  `utils/market-beta-watch.ts` — состояние там уже было общим на `window`
  (см. его комментарий), просто раньше физически лежало в каталоге одного
  конкретного модуля.
- **Общие DOM-хелперы классической страницы вынесены в `utils/market-dom.ts`**
  (тоже требование 4): разбор assetId из `javascript:BuyMarketListing(...)`
  ссылки (`getMarketRowAssetId`, раньше был приватной функцией внутри
  `market-item-attributes/apply.ts` — теперь общий, `market-item-attributes`
  сам же на него и переведён), сама ссылка как якорь для новой кнопки
  (`getMarketRowBuyLink`), список строк/бета-кнопок. Позиционное
  сопоставление беты (`betaOrder`) у обоих модулей — **независимые курсоры**
  поверх ОДНОГО и того же массива: это состояние прогресса каждого модуля
  по своему DOM, а не дублирование логики сопоставления (сама логика — один
  и тот же `betaOrder`, общий).
- **Кнопка — НЕ через `createShadowRootUi`.** В отличие от инвентарной (одна
  штука на вкладку) тут по кнопке на КАЖДУЮ строку — полноценный shadow root
  на строку был бы неоправданно тяжёлым. Вместо этого маленькая `<a>` со
  значком "↗" вставляется напрямую в light DOM сразу после родной
  Buy-ссылки/кнопки (`insertAdjacentElement('afterend', ...)`), стили —
  обычная manifest-инъекция CSS (`modules/market-pricedb-check-button/row-button.css`),
  тот же паттерн, что у `styles/item-attributes.css`: литеральные копии
  цветов из `styles/tokens.css`, без `.tf2s-root` (его `all: initial`
  сломал бы обтекание вокруг родной кнопки Steam ради одной маленькой
  ссылки на строку).
- Классика: кнопка вставляется после `div.market_listing_buy_button a`.
  Бета: после самой Buy-кнопки (`button[data-accent-color="green"]`) — оба
  случая используют один и тот же приём "вставить сразу после единственного
  стабильного элемента, который точно есть", а не пытаются угадать
  структуру хэшированного родителя.
- Как и у инвентарной кнопки — оптимистичная ссылка на поиск сразу,
  апгрейд на точную страницу предмета по готовности SKU
  (`utils/pricedb.ts#resolveSku`, тот же общий кэш/функция).

### Модули `trade-item-attributes` + `inventory-item-attributes` + `market-item-attributes` (готовые) — требование 6

Иконки/рамки предметов: unusual-эффект/strange/uncraftable/spell/
strange-parts/killstreak/lowcraft — сначала в окне трейд-оффера, затем той
же логикой распространено на инвентарь Steam и на листинги Steam Market.
Общая часть вынесена в `utils/`, чтобы не дублировать функционал
(требование 4) между тремя страницами:

- `utils/unusual-effects.ts` — карта "название Unusual-эффекта → id
  частицы", 541 запись, портирована дословно из оригинала
  (`shared.offers.unusual.effectsMap`).
- `utils/item-attributes.ts` — `getItemAttributes()`, определяет
  атрибуты по сырому Steam-объекту предмета (`descriptions`, `name_color`,
  `market_hash_name`, `type`) — регэкспы и цветовые коды скопированы
  1:1 из `shared.offers.identifiers.getItemAttributes` оригинала
  (Steam TO Enhancer), с точечными фиксами под реальный текст Steam
  (напр. префикс спелла — «Halloween: X», а не «Halloween Spell: X»
  из вики; тир killstreak определяется без привязки к началу строки,
  т.к. перед ним у Strange-предметов идёт «Strange »).
- `utils/spells.ts` + `utils/spell-icons.ts` — каталог спеллов
  (код/цвет/группа фигуры, с регистронезависимым поиском по реальному
  тексту Steam) и наборы SVG-фигур (`ghost`/`footprint`/`speaker`/
  `flame`/`pumpkin`/`flask`) для режима «Подробно»; цвет неоднородных
  спеллов (Team Spirit, Pumpkin Bombs, все paint-спеллы и т.д.) задан
  массивом стопов и рисуется линейным градиентом.
- `utils/icon-detail-level.ts` — общий тип/константы опции «Просто» /
  «Подробно» (хранится в `moduleOptions` отдельно на каждый из трёх
  модулей, см. `utils/settings.ts`).
- `utils/item-attribute-render.ts` — общий рендерer: по атрибутам и
  уровню детализации строит `.tf2s-attr-icons` (бейджи unusual/strange/
  uncraft/lowcraft + либо простые бейджи, либо SVG-иконки спеллов/
  killstreak) и вешает/снимает их с DOM-элемента предмета. Используется
  всеми тремя модулями — единственное место, которое отвечает за то, как
  выглядят значки. `PROCESSED_ATTR`, которым он помечает уже обработанный
  элемент, хранит не просто флаг "обработано", а конкретный assetId
  предмета — страницы с пагинацией (инвентарь, листинги Market)
  переиспользуют один и тот же пул DOM-узлов под РАЗНЫЕ предметы при
  смене страницы, и если бы тут был просто флаг, переиспользованный узел
  навсегда пропускал бы сканирование (баг, найденный и исправленный на
  живом инвентаре пользователя) — сверка по assetId заставляет
  перерисовать узел заново, когда Steam подменил его содержимое.
- `styles/item-attributes.css` — общий CSS для всех трёх модулей. НЕ
  через `createShadowRootUi` (в отличие от wallet-summary): классы
  вешаются на настоящие элементы страницы Steam, поэтому подключён
  обычной manifest-инъекцией (`content_scripts[].css`), без shadow root.
- `modules/trade-item-attributes/{core,apply}.ts` — MAIN world читает
  `window.g_rgAppContextData` / `g_rgPartnerAppContextData` (Steam сам
  кладёт туда полные данные предметов обеих сторон трейда на странице
  `/tradeoffer/*`); ISOLATED world находит `div.item[id^="item440_2_"]`
  (в слотах оффера и в панели выбора предметов), определяет сторону
  (`#your_slots` / `#their_slots`), передаёт атрибуты в общий рендерer.
- `modules/inventory-item-attributes/{core,apply}.ts` — страница
  инвентаря (`/id|profiles/*/inventory`) не кладёт данные предметов в
  глобальный объект заранее: Steam подгружает их постранично своими
  запросами к `/inventory/<id64>/440/2` по мере скролла. MAIN-часть
  перехватывает `window.fetch`/`XMLHttpRequest` (паттерн адаптирован из
  tf2TradingUtils `inventoryFetchBridge`) и только НАБЛЮДАЕТ эти чужие
  запросы, не дублируя их своими; ISOLATED-часть сканирует
  `.itemHolder .item[id]` (формат id тут `440_2_<assetId>`, БЕЗ
  префикса `item`, в отличие от оффера) и опрашивает MAIN-снимок на
  протяжении всей жизни вкладки (снимок растёт по мере скролла, а не
  приходит один раз). Точка входа MAIN-части (`inventory-attributes-core.
  content.ts`) явно задаёт `runAt: 'document_start'` — без этого (баг,
  найденный и исправленный на живом инвентаре пользователя) манифест по
  умолчанию ставит `document_idle`, и перехват fetch/XHR встаёт ПОЗЖЕ,
  чем страница успевает сделать свои первые запросы за первую партию
  предметов — те запросы проходят мимо перехвата и их предметы навсегда
  остаются без иконок.
- `modules/market-item-attributes/{core,apply}.ts` — страница листингов
  конкретного предмета (`/market/listings/440/*`), ДВЕ ветки в зависимости
  от того, какую версию страницы Steam сейчас показывает:
  - **Классика**: `window.g_rgAssets['440']['2']` синхронно даёт данные
    всех видимых листингов (как оффер, не как инвентарь — перехватывать
    сеть тут не нужно). ISOLATED-часть находит assetId каждой строки не по
    `id` элемента (там его нет), а разбором
    `javascript:BuyMarketListing(...)` ссылки кнопки "Buy" (портировано из
    tf2trader); иконка предмета тут рисуется через `<img
    class="market_listing_item_img">`, а не CSS-фоном, как на
    офере/инвентаре, — поэтому в `styles/item-attributes.css` добавлено
    одно точечное правило, которое делает эту картинку прозрачной именно у
    unusual-предметов, чтобы фон-эффект, который ставит общий рендерer,
    был виден сквозь неё.
  - **Бета** (экспериментально, `utils/market-beta-watch.ts`):
    `g_rgAssets` нет — вместо неё перехватываются собственные fetch-запросы
    страницы к `/market/actions?q=QueryListingsForItem` (тот же приём, что
    у `utils/inventory-watch.ts`). Самый первый батч листингов не проходит
    через видимый fetch (отрисован на сервере) — добирается отдельным
    same-origin запросом с теми же параметрами (`start:0`), который
    `beta-watch.ts` делает сам при установке перехвата. Иконка предмета —
    обычный `div` с фоном через CSS custom property `--bg-image`; unusual-
    эффект просто перезаписывает это инлайн-стилем (инлайн всегда
    побеждает по специфичности, доп. CSS-правило не нужно, в отличие от
    классики). Подробности про позиционное (не по id) сопоставление
    карточки с данными — см. "Известное ограничение" выше и комментарий в
    начале `beta-watch.ts`.

### Модуль `scrap-item-modal` (готовый)

Первый готовый модуль для **scrap.tf** (`scrapTf` в реестре). Плавающее
окошко, которое появляется по среднему клику или Ctrl/Cmd+клику на любой
предмет (страницы `/buy/*` — weapons, hats и т.д. — и `/auctions`,
`/auctions/<код>`) — портировано из **tf2TradingUtils**
(`scrap.tf/itemLinks/content.js`), но с двумя сознательными отличиями от
оригинала, обе разобраны ниже.

**`scrap-table-links` убрана из реестра.** Изначально реестр описывал для
scrap.tf три функции, в том числе ссылки прямо в ячейках таблицы личного
item banking (`#itembanking-list`, `/bank`). Прежде чем её кодить,
понадобился живой HTML этой страницы (тот же принцип, что и у всех
DOM-модулей этого проекта) — но пользователь не смог найти такую страницу
у себя ("scrap.tf/bank чет найти не могу, в интернете страницы нет") и
явно попросил убрать функцию из реестра, а не гадать по устаревшему
tf2TradingUtils-референсу. Строка полностью удалена из
`utils/registry.ts` (с комментарием на месте — если пользователь позже
найдёт эту страницу под другим адресом, функцию можно будет вернуть).

**Откуда данные о предмете — НЕ из живой подсказки, как в оригинале.**
Оригинальный `itemLinks/content.js` при клике читает
`document.querySelector(".hover-over")` — единственный на всю страницу
элемент, который сайт сам заполняет текстом наведённого предмета, и
обрывается, если тот ещё не показан (`selectedHoverEl.style.display ===
"none"`) — то есть Ctrl+клик без предварительного наведения у оригинала
не сработал бы. Здесь вместо этого атрибуты читаются прямо с самого
кликнутого `.item.hoverable` — `data-title`/`data-content` (тот же самый
текст, которым сайт заполняет свою подсказку, но уже лежащий на каждом
предмете индивидуально) плюс классы `qualityN`/`killstreakN`/`uncraft` на
самом div'е (`modules/scrap-item-modal/attributes.ts`). Это надёжнее (не
зависит от состояния наведения) и работает одинаково на всех подтверждённых
живым HTML страницах — `/buy/weapons`, `/buy/hats`, `/auctions`,
`/auctions/SRRHAB` (все четыре прислал пользователь как `view-source:`).

**Изначально 4 ссылки из описания реестра, по ходу сужено до одной —
PriceDB.io.** Реестр сперва описывал модуль как "bp.tf stats/classifieds,
Steam Market, Wiki" — уже сокращённый набор относительно оригинала (тот
строит все 12: ещё mannco.store/skinport.com/marketplace.tf/crate.tf/
merchant.tf/gladiator.tf/pricedb.io/liquid.tf, с собственной ~180Кб
TF2-схемой ради defindex-based ссылок). Пользователь по ходу реализации
явно попросил сузить ещё раз — той же самой мыслью, что уже применена в
`stn-item-links`: вместо 4 отдельно построенных ссылок одна кнопка
"Проверить на PriceDB.io" (`utils/pricedb.ts` — тот же SKU-резолвер, что и
в `pricedb-check-button`/`market-pricedb-check-button`/`stn-item-links`,
requirement 4), а сама страница предмета на PriceDB.io уже ссылается на
добрый десяток площадок разом, включая Steam Market и backpack.tf
(подтверждено живым запросом при разработке `stn-item-links`). Как и там,
для Unusual-предметов имя для резолвера строится в формате "<эффект>
<имя>" без слова "Unusual" (`modules/scrap-item-modal/links.ts#buildPricedbPriceableName`,
эффект берётся из строки "Effect: X" в `data-content`) — иначе резолвер не
находит нужный вариант. Ссылка сперва ведёт на страницу поиска
(`pricedbSearchUrl`), а как только резолвится SKU — незаметно апгрейдится
на точную страницу предмета (`pricedbItemUrl`), тот же приём, что у
`stn-item-links#buildLink`.

**Активация — настраиваемая комбинация, а не жёстко средний клик/
Ctrl+клик.** Первая версия поддерживала ровно два зашитых триггера —
средний клик (то, что пользователь описал буквально: "тыкаем средней
кнопкой мышки СКМ") и Ctrl/Cmd+левый клик как мой собственный запасной
вариант для трекпадов. По следующей прямой просьбе пользователя
("сделать чтобы пользователь сам мог задать бинд, а не чтобы только Ctrl
или СКМ") это заменено на ОДНУ полностью настраиваемую комбинацию —
`modules/scrap-item-modal/trigger.ts` (`{ button: 'left'|'middle'|'right',
ctrl, alt, shift, meta }`, хранится как module option, тот же механизм,
что и режим `trade-item-summary`/уровень детализации иконок — см.
`utils/settings.ts#getModuleOption`). По умолчанию — средняя кнопка без
модификаторов (буквально исходный запрос), настраивается на странице
опций: кнопка "Записать" вооружает разовые `mousedown`/`contextmenu`/
`keydown`(Esc-отмена) слушатели на `window` (не на самой кнопке — так
запись работает для любой комбинации где угодно на странице, а не только
по клику ровно на этой кнопке), следующее нажатие мыши становится новым
биндом (`components/FeatureToggle.vue`).

Сопоставление события с настроенным триггером — `matchesScrapModalTrigger`,
ТОЧНОЕ совпадение по кнопке И по каждому модификатору (не "хотя бы эти", а
"ровно эти") — предсказуемее для системы биндов, Ctrl+клик и
Ctrl+Shift+клик не путаются между собой. Три обработчика на `document`
(capture-фаза), у каждого своя причина, зависящая от того, какая кнопка
сейчас настроена:
- `mousedown` — сама активация, для ЛЮБОЙ настроенной кнопки.
  `preventDefault()` там же гасит побочные эффекты (автопрокрутка по
  средней и т.п.). Chrome не генерирует `'click'` на среднюю/правую кнопку
  вообще (только `'auxclick'`/`'contextmenu'`) — поэтому `mousedown`
  единственное событие, которое приходит одинаково для любой кнопки.
- `click` — нужен, ТОЛЬКО когда настроена ЛЕВАЯ кнопка: гасит нативный
  `onclick="ScrapTF.Auctions.RedirectToAuction(...)"` на всей карточке
  аукциона (подтверждено живым HTML `/auctions` — висит на
  `.panel-raffle-items`, слушает именно `'click'`, а не `'mousedown'` —
  `stopPropagation()` на mousedown его бы не остановил). Для средней/правой
  кнопки не нужен — Chrome в принципе не порождает для них `'click'`.
- `contextmenu` — нужен, ТОЛЬКО когда настроена ПРАВАЯ кнопка: без него
  браузер всё равно откроет родное меню поверх только что открытого окна.
  Завязан на флаг `suppressNextContextMenu`, который выставляет сам
  `mousedown`-обработчик в момент реальной активации — гасится именно то
  нажатие, что сработало, а не пересчитывается заново по модификаторам.

**`scrap-pricedb-context-menu` убрана из реестра как дублирующая.** Этот
planned-модуль ("PriceDB.io по правому клику") описывал ровно ту же саму
цель — открыть PriceDB.io по клику на предмете, просто жёстко на правой
кнопке. Раз кнопка активации `scrap-item-modal` теперь настраивается
пользователем, включая правую, отдельный модуль под то же самое дублировал
бы функционал (requirement 4) — убран из `utils/registry.ts` по прямой
просьбе пользователя, с комментарием на месте.

**Окно — перемещаемое И регулируемое по размеру, обе возможности прямо
запрошены пользователем.** Перетаскивание за заголовок — тот же приём
(Pointer Events, запоминание позиции в `localStorage`), что уже
используется в `modules/wallet-summary/panel.ts` — единственная в проекте
панель того же типа "плавающее окно поверх страницы". Регулировка
размера — родное CSS `resize: both` на самой панели вместо своего
перетаскивания уголка мышью (браузер уже умеет это надёжно и
кроссбраузерно сам); итоговый размер после ресайза запоминается через
`ResizeObserver`, тем же способом, что и позиция — оба переживают
обновление страницы. Одно постоянное окно на вкладку (создаётся один раз
при монтировании, дальше только переиспользуется и обновляет содержимое —
как и в оригинале), с кнопкой закрытия — по умолчанию скрыто до первого
клика по предмету.

**Страницы — весь scrap.tf, а не только изначально проверенные.**
Изначально `matches` содержал только `/buy/*` и `/auctions*` — страницы, для
которых был живой HTML. Пользователь сообщил, что модалка не работает на
`/unusuals/89` (туда не входила), и попросил взять весь домен —
`matches: ['*://scrap.tf/*']`. Живой HTML именно `/unusuals/*` не
присылался — расширение сделано по инференции, не по проверке: `.item.
hoverable` уже подтверждён идентичным на двух ПО-РАЗНОМУ устроенных
страницах (сеточный `/buy/*` и карточки-аукционы `/auctions`), значит это
общий для сайта компонент карточки предмета, а не разметка конкретной
страницы — почти наверняка тот же и на `/unusuals`, `/sell` и любых
будущих страницах листинга. Риск ограничен: обработчик реагирует только на
клик по `.item.hoverable`, на любой другой разметке домена (включая
несуществующую `/bank`) он просто ничего не находит и не активируется —
никакого поведения на не-товарных страницах не меняется. Если на какой-то
странице карточка всё же устроена иначе — модалка там молча не появится
(не упадёт с ошибкой), но и не подтверждена живым тестом, в отличие от
исходных четырёх страниц.

**Известное ограничение — War Paint / decorated-оружие (`quality15`).**
Подтверждено живым HTML (карточки аукционов с `class="skin-preview"`), но
их настоящее имя устроено принципиально иначе — паттерн раскраски +
степень изношенности (напр. "War Paint: Cutter's Fever (Field-Tested)"),
а не просто "качество + название", как у всех остальных 9 качеств. Эта
логика нигде в проекте не реализована — для decorated-оружия используется
базовое имя из `data-title` как есть, PriceDB.io может не распознать
такой вариант и откатиться на страницу поиска вместо точной страницы
предмета (то же осознанное упрощение, что уже принято в
`market-pricedb-check-button`/`stn-item-links` для похожих краевых
случаев).

### Модуль `steam-profile-links` (готовый)

Ссылки на backpack.tf/steamhistory.net/posts.tf + бейдж SteamID64/SteamID32/
SteamID — прямо на главной странице профиля
Steam, "в дизайне Стима", сразу после раздела «Иллюстрации» — по прямой
просьбе пользователя, с двумя скриншотами нужного места в чате. Заменяет
собой два изначально planned-модуля разом — `trade-partner-links` (ссылки
на партнёра на странице оффера) и `profile-links` (те же ссылки в списках
офферов): вместо того, чтобы строить одинаковые ссылки в двух разных
местах, они теперь строятся один раз — прямо на самой странице профиля
того пользователя, куда и так можно перейти по клику на имя из оффера или
списка (requirement 4, "не повторять функционал").

**Где вставляем — живой DOM.** Проверено JS-инспекцией реального профиля
(`steamcommunity.com/id/rakovaya_opuhol/`, тот самый профиль со
скриншотов пользователя): ряд "Игры / Инвентарь / Скриншоты / Работы в
мастерской / Обзоры / Иллюстрации" — это `<div class="profile_item_links">`,
внутри — `<div class="profile_count_link ellipsis">` на каждый пункт
(ссылка + счётчик), последним ребёнком — `<div style="clear: left;">`.
"Иллюстрации" (Artwork) — последний реальный пункт перед этим clear-div'ом,
ровно там, куда пользователь просил вставить новые ссылки. Свои пункты
вставляются в тот же ряд, перед clear-div'ом, ТЕМИ ЖЕ классами
(`profile_count_link ellipsis`) — их CSS уже загружен на странице, поэтому
"в дизайне Стима" достигается бесплатно, без единого литерального
цвета/отступа с нашей стороны (тот же приём, что у `stn-item-links` с их
bootstrap-классами). Страницы вроде `/inventory`, `/games` и т.д. этого
блока не содержат (проверено — на `/inventory` `.profile_item_links` в DOM
просто нет), поэтому матчится весь `steamcommunity.com/id/*` и
`/profiles/*` (как и у `scrap-item-modal` — широкий матч + матчер на
конкретный селектор, который просто ничего не находит на "чужих"
подстраницах и молча не срабатывает — риска что-то сломать там нет).

**Откуда SteamID64.** НЕ из `g_rgProfileData` (MAIN-мир страницы,
недоступен обычному ISOLATED content-скрипту без инъекции `<script>`) — у
аватара в шапке профиля (`.playerAvatar.profile_header_size`) есть обычный
DOM-атрибут `data-miniprofile="77887257"` — это accountID (32-битная часть
SteamID64). Проверено живым сравнением на том же профиле:
`g_rgProfileData.steamid` = `"76561198038152985"`, и
76561198038152985 − 76561197960265728 (стандартный публичный оффсет Valve)
= 77887257 — сходится ровно. Дальше SteamID64/SteamID32/классический
SteamID — чистая арифметика (см. `modules/steam-profile-links/steamid.ts`,
`BigInt`, т.к. SteamID64 уже превышает `Number.MAX_SAFE_INTEGER`). Работает
одинаково для СВОЕГО профиля и для профиля любого другого пользователя
(партнёра по трейду) — один и тот же DOM-атрибут что там, что там, что и
позволило заменить оба изначальных planned-модуля одним.

**Ссылки.** `backpack.tf/profiles/<steamid64>` (общеизвестный устоявшийся
формат в TF2-трейдинге), `steamhistory.net/id/<steamid64>` (формат из
примера, который прислал пользователь), `posts.tf/users/<steamid64>`
(подтверждено живым переходом — открылся реальный чужой профиль,
`posts.tf/users/76561198079732098` → "bibblée's profile | posts.tf").

**Бейдж SteamID.** Отдельный пункт-кнопка в том же ряду — по клику
открывает маленький попап с тремя форматами (SteamID64/SteamID32/
классический `STEAM_0:Y:Z`) и кнопкой копирования у каждого. Это, в
отличие от остальных пунктов ряда, НЕ стимовский дизайн — Steam ничего
подобного нативно не показывает, поэтому здесь как раз уместна собственная
палитра расширения (`styles/tokens.css`, `.tf2s-root`/`.tf2s-panel`), тот же
приём, что и у любого другого всплывающего окна TF2 Trade Suite Tools (напр.
`scrap-item-modal`). Закрывается по клику снаружи или по Esc.

**Community Bans — отдельный пункт сознательно убран.** Изначально был ещё
один пункт-кнопка "Community Bans ↗", но он вёл на ТУ ЖЕ ссылку
steamhistory.net, что и обычный пункт "SteamHistory" рядом — по факту
просто дублировал его. Причина, по которой это не был полноценный
встроенный бан-статус, а именно ссылка — честная: steamhistory.net (и
backpack.tf тоже) при заходе, даже из настоящего браузера, не headless,
отдаёт экран проверки безопасности (Cloudflare) вместо страницы, так что
даже живой просмотр разметки конкретно бан-статуса (нужный, чтобы найти
правильные CSS-классы/структуру) оказался недоступен — а писать код,
парсящий чужую HTML-структуру, которую ни разу не видел, значило бы гадать
вслепую (см. выше про живой HTML вместо догадок). Раз честно встроить
статус нельзя, а вести на ту же ссылку, что уже есть — просто дублирование,
по прямой просьбе пользователя лишний пункт убран целиком ("если не
получается его сделать — лучше просто убрать эту ссылку, тк у нас и так

— по обычному пункту "SteamHistory" в этом же ряду.

### Модуль `instant-accept-decline` (готовый)

Кнопки "Принять"/"Отклонить" прямо в списке входящих офферов
(`/tradeoffers`), без перехода на страницу отдельного оффера.

**Живой HTML.** Пользователь прислал полный исходник своей реальной
страницы `/tradeoffers` (5 активных офферов на момент проверки — совпало с
тем, что показывал сайдбар "Incoming Offers (5)"). Каждая строка — `<div
class="tradeoffer" id="tradeofferid_9343679954">`; у АКТИВНЫХ (ожидающих
ответа) офферов внутри есть `.tradeoffer_footer_actions` с готовыми
ссылками `javascript:ShowTradeOffer('id')` ("Respond to Offer") и
`javascript:DeclineTradeOffer('id')` ("Decline Trade") — у уже обработанных
(принятых/отклонённых/отменённых, показанных на той же странице как
история) этого блока в разметке просто нет — заменён на
`.tradeoffer_items_banner` с текстом вроде "Trade Accepted...". Наличие
`.tradeoffer_footer_actions` — одновременно и признак "это активный
оффер", и точка вставки: гадать состояние по каким-то другим классам не
пришлось.

**Почему "мгновенные", хотя Decline у Steam и так мгновенный.** "Decline
Trade" у Steam уже вызывает `DeclineTradeOffer()` без перезагрузки/перехода
— то есть половина фичи из названия технически уже есть нативно. Чего
ДЕЙСТВИТЕЛЬНО не хватает — мгновенного ACCEPT: "Respond to Offer" лишь
открывает страницу самого оффера, где принять можно только там. Поэтому
добавлены свои кнопки "Принять"/"Отклонить" (обе, не только принять) —
через собственный AJAX-клиент (`utils/steam-trade-offer-api.ts`), а не
через нативный `DeclineTradeOffer` — так обе кнопки одинаково
самодостаточны и визуально симметричная пара, а не "новая кнопка рядом со
старой ссылкой". Нативные "Respond to Offer | Decline Trade" не убираются
— добавление чисто аддитивное.

**Сетевой контракт — не угадан, а взят как есть.** Разметка страницы
списка офферов не содержит готового JS-вызова именно для accept (только
`ShowTradeOffer`/`DeclineTradeOffer`, обе — MAIN-мир-функции страницы,
недоступные ISOLATED content-скрипту напрямую). Вместо того, чтобы гадать
по минифицированному JS Steam, использован независимо документированный,
годами стабильный публичный контракт самого steamcommunity.com (тот же,
которым пользуется указанный в `utils/registry.ts` как `portedFrom`
источник — Steam Trade Offer Enhancer — и множество независимых
трейд-инструментов):
`POST /tradeoffer/<id>/decline` с телом `sessionid`, и
`POST /tradeoffer/<id>/accept` с телом `sessionid, serverid=1,
tradeofferid, partner=<SteamID64 партнёра>, captcha=''`. `sessionid` —
читается из cookie `sessionid` (не из MAIN-мир `g_sessionID` — в живом
HTML пользователя оба значения совпадали), SteamID64 партнёра — из
`.tradeoffer_partner .playerAvatar[data-miniprofile]` той же строки, тем же
способом, что и у `steam-profile-links` (`data-miniprofile` = accountID,
см. `utils/steamid.ts`, вынесенный туда из `steam-profile-links`, чтобы не
дублировать конвертацию между двумя модулями — requirement 4).

**Подтверждение.** У "Принять" — да, `window.confirm` (реальная,
необратимая по сути операция, даже если Steam потом попросит мобильное
подтверждение — сам запрос уже ушёл). У "Отклонить" — нет, как и у
нативной ссылки рядом: отклонение безопасно и обратимо, партнёр всегда
может прислать оффер заново. Ответ Steam на accept может содержать
`needs_mobile_confirmation`/`needs_email_confirmation` — это не ошибка, а
отдельный статус, так и показан пользователю ("Отправлено — подтвердите в
мобильном приложении Steam").

**Область действия.** Только `/tradeoffers` (входящие) — НЕ
`/tradeoffers/sent` (свои исходящие можно только Cancel, это другая по
смыслу операция) и не `/tradehistory`. Match-паттерн WXT не умеет выразить
"всё, кроме конкретного хвоста", поэтому `/sent` отсекается рантайм-
проверкой `window.location.pathname` внутри самого модуля, а не в
матчере — живой HTML `/sent` не проверялся, поэтому там код и не пытается
угадывать разметку.

**Найденный после первого релиза баг: HTTP 403 на "Принять".** В реальном
использовании пользователь получил `HTTP 403` именно на accept (decline
работал нормально). Причина — Steam на `/tradeoffer/<id>/accept` (и,
возможно, `/decline`) проверяет заголовок `Referer`: он должен быть
страницей САМОГО оффера (`https://steamcommunity.com/tradeoffer/<id>/`), а
не страницей `/tradeoffers`, с которой реально уходит запрос. Обычный
`fetch()` без опции `referrer` шлёт в качестве Referer как раз страницу
отправки запроса — Steam её для accept не принимает. Исправлено передачей
`referrer: \`https://steamcommunity.com/tradeoffer/${offerId}/\`` в опции
`fetch()` (`utils/steam-trade-offer-api.ts`) — это тот же URL, просто
same-origin, так что браузер это разрешает без дополнительных прав.
Подтверждено пользователем как исправление ("всё, работает").

### Модуль `decline-all-active` (готовый)

Одна кнопка над списком входящих офферов, отклоняющая сразу ВСЕ активные
(ожидающие ответа) офферы — с подтверждением перед стартом.
`defaultEnabled: false` в `utils/registry.ts` — единственный ready-модуль
проекта, у которого это осознанно так: массовое необратимое действие не
должно включаться само по себе, тумблер в настройках включает вручную.

Переиспользует ту же живую разметку и тот же AJAX-клиент decline, что и
`instant-accept-decline` (`utils/steam-trade-offer-api.ts` — requirement 4,
общий сетевой код не продублирован): "активный" оффер — строка
`.tradeoffer`, у которой есть `.tradeoffer_footer_actions`.

**Где вставляем.** Кнопка вставляется один раз, перед первой строкой
`.tradeoffer`, и только если активных офферов ≥ 1 — нечего отклонять,
незачем показывать кнопку. Список отклоняемых офферов — снимок на момент
показа кнопки (рендерится один раз за заход на страницу); если пользователь
до клика вручную обработал один из них через `instant-accept-decline`,
повторный decline на уже неактуальный id у Steam просто вернёт ошибку для
этой одной строки, без последствий для остальных — статус по каждой строке
показывается отдельно.

**Темп запросов.** Отклонения идут последовательно с паузой 350мс между
запросами, а не все параллельно разом — тот же осторожный темп, которого
придерживается большинство сторонних трейд-инструментов при массовых
операциях, чтобы не заваливать Steam очередью запросов.

**Область действия** — та же логика отсечения `/tradeoffers/sent`
рантайм-проверкой пути, что и у `instant-accept-decline` (см. выше), по той
же причине.

проекта под next.backpack.tf тоже нет соответствующей oldUI-реализации —
там отдельный, гораздо более простой модуль (`newUI/addKSButton`, React-
компонент вместо content-скрипта над чужим DOM), который не подошёл бы для
переиспользования тем же кодом. Поэтому здесь, в отличие от
`bptf-listing-trade-params` (который явно поддерживает оба варианта
интерфейса), намеренно поддержан только один.

**Главная причина, по которой модуль вообще в таком виде — прямая просьба
пользователя перед реализацией:** не у каждого предмета TF2 есть Killstreak
Kit — кнопки переключения тиров должны появляться только там, где это имеет
смысл, а не на любом предмете подряд. Портирован список
`KILLSTREAK_WEAPONS_SET` (`utils/killstreak-weapons.ts`, ~140 голых имён
оружия, источник — прайслист китов kits.tf) — модуль не рисует ничего, если
имя текущего предмета страницы в этот список не попало. Это не то же самое,
что уже существующий в проекте `utils/killstreak.ts` (requirement 4, не
дублируем): тот определяет тир/Sheen/Killstreaker УЖЕ имеющегося
killstreak-предмета по его описанию (для бейджей на своих предметах), а
`killstreak-weapons.ts` — наоборот, список того, какое оружие в принципе
можно killstreak-нуть, когда доступно только голое имя из URL страницы
backpack.tf, без самого предмета с описанием.

**Живой HTML.** Проверено на реальных страницах пользователя (полный
исходник вставлен в чат, не WebFetch-конвертация — точные классы важны):

- `/stats/Strange/Rocket%20Launcher/Tradable/Craftable`: внутри
  `.stats-header-controls` первым div-потомком идёт нативный пикер
  качества/скина `.btn-group.btn-group-sm.stats-quality-list` — точка
  вставки нашей строки кнопок сразу после него (плюс разделительный
  `<br>`, как в оригинале).
- `/classifieds?item=Rocket%20Launcher&quality=11&tradable=1&craftable=1
  &australium=-1&killstreak_tier=0&spell=None`: внутри `.panel.panel-main
  .panel-body` есть готовый ряд крошек-фильтров `#search-crumbs`
  (Item/Quality/Tradable/Craftable/Australium/Killstreak Tier/Spell) —
  точка вставки нашего `#ks-tier-nav` сразу после него.
  `killstreak_tier` подтверждён как реальный, рабочий query-параметр —
  виден в href ссылки "Expand" одного из настоящих листингов на странице.
- На обеих страницах `#ks-tier-nav`/`.stats-killstreak-list` на момент
  проверки не существовало — фича действительно не реализована нативно.

**backpack.tf недоступен мне для самостоятельной проверки.** Как и
steamhistory.net ранее в проекте, backpack.tf защищён Cloudflare Turnstile
("Подтвердите, что вы человек") — встроенный браузер упёрся в чекбокс-вызов.
Обход CAPTCHA прямо запрещён — вместо попытки обойти пользователю было
предложено прислать живой HTML напрямую, что и стало основным источником
разметки выше вместо догадок по чужому исходнику.

**Без `MutationObserver`,** в отличие от `bptf-listing-trade-params`: там он
нужен из-за AJAX-подгрузки объявлений без перезагрузки страницы, но
`.stats-header-controls`/`#search-crumbs` — статичная часть разметки,
приходит сразу с сервера при каждой полной загрузке страницы, а смена
фильтров/пагинация на classic backpack.tf/classifieds — обычные переходы по
ссылке, не SPA-навигация. Одного прохода при старте content-скрипта
достаточно.

**Как собираются ссылки.** На `/stats` тир вшивается прямо в имя предмета
(отдельного поля под килстрик там нет) — например, кнопка "Professional KS"
для Rocket Launcher ведёт на `/stats/Strange/Professional%20Killstreak%20
Rocket%20Launcher/Tradable/Craftable`. На `/classifieds` — обычный
query-параметр `killstreak_tier=0..3`, с сохранением всех остальных активных
фильтров и сбросом `page` на `1` (смена тира меняет набор результатов —
старый номер страницы мог перестать существовать).

**Стилизация** — нативными bootstrap-классами backpack.tf (`btn
btn-variety` на /stats, `btn btn-default` на /classifieds), а не своей
дизайн-системой `styles/tokens.css` — та же логика, что у
`stn-item-links.css`: встраиваемся рядом с их собственными кнопками,
чужая палитра выглядела бы инородно. Цвета текста кнопок — оригинальные
цвета backpack.tf для этих тиров (`#000000`/`#5B6060`/`#68765C`/`#B15820`),
не выдуманные.

**Исключения.** "Мои листинги" (`/classifieds?steamid=...`) и архив
(`/classifieds/archive`) показывают сразу много разных предметов одного
пользователя — фильтр килстрик-тира ОДНОГО предмета там не имеет смысла,
перенесено из оригинала как есть.

**Добавлено позже: фильтр по Sheen/Killstreaker.** Пользователь попросил
"не кучу кнопок" под конкретные эффекты, а возможность выбрать нужную
конфигурацию (например, только Tornado или Tornado + что-то ещё). Оказалось,
у самого backpack.tf уже есть родной фильтр под это — просто он спрятан в
JS-рендерящуюся модалку Advanced Search (кнопка "Advanced" рядом с полем
поиска), которой не было в статичном HTML страницы, поэтому её пришлось
попросить открыть и прислать отдельно. Внутри — чекбоксы `data-key="sheen"`
(1–7: Team Shine/Deadly Daffodil/Manndarin/Mean Green/Agonizing
Emerald/Villainous Violet/Hot Rod) и `data-key="killstreaker"`
(2002–2008: Fire Horns/Cerebral Discharge/Tornado/Flames/Singularity/
Incinerator/Hypno-Beam), с их же комментарием прямо в разметке про
конфликты: Sheen не бывает у No Kit/Standard, Killstreaker — вообще только
у Professional. Формат итогового URL при нескольких значениях подтверждён
4 живыми примерами пользователя (открыл модалку → отметил чекбоксы →
Confirm → прислал адрес страницы): значения одного фильтра склеиваются
через запятую в одном параметре — `&sheen=3,7&killstreaker=2004,2008`
(`URLSearchParams` кодирует запятую как `%2C` сама, вручную ничего доделывать
не пришлось).

Реализовано как расширение ЭТОГО ЖЕ модуля (не отдельным тумблером) —
выпадашка "Эффекты ▾" появляется рядом с кнопками тиров только когда выбран
Specialized (тогда видна только секция Sheen) или Professional (Sheen +
Killstreaker), с чекбоксами и кнопками "Применить"/"Сбросить". При
переключении тира кнопками (см. выше) параметры `sheen`/`killstreaker`
теперь тоже вычищаются, если для нового тира они уже недействительны — чтобы
не тащить в URL комбинацию, которую сам backpack.tf считает конфликтом.

Открытие/закрытие выпадашки — своим обработчиком клика (класс `.open` на
`.btn-group`, снимается кликом вне неё), а не через `data-toggle="dropdown"`
их Bootstrap: живым тестом подтверждены только `modal`/`collapse` (сама
модалка и аккордеон её панелей), а `dropdown.js` — нет, полагаться на
неподтверждённый JS-плагин не стали. CSS-классы (`btn-group`,
`dropdown-menu`, `open`) при этом свои же, из общего bootstrap.css страницы —
позиционирование и показ панели работают без единого собственного правила
`position`.

### Модуль `bptf-filter-special` (готовый)

Кнопки "Только spells" / "Только strange parts" над списком объявлений
(Sell Orders / Buy Orders) на classic backpack.tf — `/classifieds*` и
`/stats/*`.

**Инверсия по прямой просьбе пользователя.** В `utils/registry.ts` фича
изначально была описана как "Скрыть спеллы/strange parts в листингах" — это
и есть исходное поведение портируемого `filterSpecialListings`
(tf2TradingUtils): по умолчанию ПРЯЧЕТ такие лоты, одна кнопка их
возвращает. Пользователь явно попросил ровно наоборот — ничего не прятать
по умолчанию, а по требованию ПОКАЗЫВАТЬ ТОЛЬКО нужную категорию: отдельная
кнопка под spells, отдельная под strange parts. На уточняющий вопрос про
поведение при нажатии обеих сразу пользователь выбрал ИЛИ (объединение, не
пересечение) — виден любой лот хотя бы с одним из двух отмеченных
атрибутов, а не только те, что несут оба сразу.

**Детектор самого атрибута** — портирован без изменений (он не зависел от
направления hide/show): у `.item` внутри каждого `<li class="listing">`
есть по одному `data-spell_N` / `data-part_name_N` атрибуту на каждый
спелл/strange part предмета — наличие любого атрибута с таким префиксом и
есть признак. Проверено на живых лотах реального `/classifieds` пользователя
(вставлен в чат целиком) — сегодня работает ровно так же: у лота со strange
parts — `.item[data-part_name_1="Dominations"][data-part_score_1="0"]
[data-part_price_1="6.55–6.85 keys"]...` (несколько частей нумеруются
подряд, в заголовке лота рядом с именем предмета ещё и текстом видно
`<small>Parts Attached</small>`, но в детекторе не используется — атрибут
надёжнее, не завязан на текст конкретной локали страницы); у лота со
спеллом — `.item[data-spell_1="Weapon Spell: Exorcism"]`, аналогично.

**Обе страницы одним кодом.** `ul.media-list`/`li.listing` — общая разметка
и для `/classifieds`, и для `/stats` (то же самое уже подтверждено
`bptf-listing-trade-params`, который разбирает `.listing` единым кодом без
ветвления по странице — см. его раздел выше), поэтому здесь тоже нет
отдельных путей под каждую. `MutationObserver` нужен по той же причине, что
и там: на `/stats` объявления могут подгружаться AJAX'ом без перезагрузки
страницы, на `/classifieds` пагинация — обычные переходы по ссылке (полная
перезагрузка), но ради этого различия отдельный путь заводить не стали —
один наблюдатель безопасно работает на обеих.

**Кнопка добавляется, только если она действительно нужна** — если в
конкретном списке (Sell или Buy Orders по отдельности) нет ни одного лота
со спеллом, кнопки "Только spells" там не будет вовсе (и наоборот) — вместо
двух кнопок всегда может оказаться одна или ни одной, если фильтровать
нечего.

### Модуль `bptf-price-graph` (готовый)

Встроенный график цены PriceDB.io на странице предмета classic backpack.tf
(`/stats/<Quality>/<Item>/Tradable/Craftable...`) — прямо перед списком
объявлений.

**Сам график — просто iframe, без своего чарта.** PriceDB.io отдаёт готовую
картинку графика по SKU через `https://pricedb.io/api/graph/<sku>` — рисовать
что-то самим (библиотека графиков, запрос истории цен) не нужно, ровно тот
же приём, что у портируемого `tf2trader` (`utils/graph.ts
#createPricedbGraphIframe`).

**Точка вставки — по прямой просьбе пользователя другая, чем у оригинала.**
tf2trader вставляет график перед `.guttered:has(.stats-graph)` — это
нативный график Timeline ВВЕРХУ страницы, первая секция после заголовка
предмета. Пользователь явно попросил другое место: "я бы хотел чтобы он был
сверху перед листинингами а не как в оригинале снизу... хочу видеть это
перед надписью Classifieds". Устойчивый якорь для этого — `<h2
id="classifieds">` — живым HTML подтверждено на двух разных страницах
предметов с разным набором секций статистики перед ней:

- `.../Strange/Specialized%20Killstreak%20Rocket%20Launcher/...`: Timeline →
  "Strange Parts" → Classifieds;
- `.../Haunted/Crone's%20Dome/...`: Timeline → "Paint Distribution" →
  "Level Distribution" → Classifieds.

В обоих случаях сразу после `<h2 id="classifieds">` идёт
`<div class="guttered"><div class="row">` с Sell/Buy Orders — то есть сам
якорь не зависит от набора необязательных секций конкретного предмета.
`moveClassifiedsToTop()` оригинала (физическая перестановка всей секции
Classifieds в начало страницы) не портируется — это отдельная, не
запрошенная функциональность, как и его кнопка "Copy !add" для автобота.

**Стиль — под нативные секции backpack.tf, а не тёмный бокс оригинала.**
Оригинал оборачивает iframe в свой собственный див с inline-стилями
(`background:#1b1b1b;border:1px solid #222`), заметно выделяющийся на
светлой панели backpack.tf. По просьбе пользователя ("стилизовавать его под
бэкпак тф") здесь вместо этого — их же разметка, скопированная с нативных
нижних секций статистики: пара `<h2>` + `<div class="guttered"><div
class="stats-graph">...</div></div>`, тот же паттерн, что у любой их родной
секции с графиком. Свой CSS нужен только для размера самого `<iframe>` (у
backpack.tf `.stats-graph` обычно рисует собственный JS-график, а не
встраивает чужой документ).

**SKU для графика — два уровня, с фолбэком, которого нет у оригинала.**
Оригинал берёт SKU только из родной ссылки на Marketplace.tf на странице
предмета (`getSkuFromMarketplaceLink`). Живым HTML подтверждено, что эта
ссылка есть не у каждого предмета: у Haunted Crone's Dome в блоке price-box
была ссылка `<a class="price-box"
href="https://marketplace.tf/partneritem?sku=920;13&attrib=bp">`, а у
Strange Specialized Killstreak Rocket Launcher — только ссылка на Steam
Community Market, без Marketplace.tf вовсе. Поэтому здесь два уровня:

1. Если ссылка `a.price-box[href*="marketplace.tf/partneritem"]` есть —
   берём SKU из её query-параметра `sku` напрямую, без единого сетевого
   запроса.
2. Если её нет — уже реализованный в проекте `utils/pricedb.ts#resolveSku`
   (тот же провайдер PriceDB.io, свой SKU-резолвер по человеческому имени;
   используется также `pricedb-check-button`/`market-pricedb-check-button`/
   `trade-item-summary` — требование "не дублировать функционал") по имени
   Quality + Item из сегментов текущего пути `/stats/...`. Формат пути и
   индексы сегментов — не новая догадка, а уже подтверждённая живым HTML
   разметка, используемая (для другой цели — сверки с оружием) в
   `bptf-ks-tier-buttons/core.ts#getBaseWeaponName`: `['', 'stats', Quality,
   Item, 'Tradable', 'Craftable'|'Non-Craftable', EffectId?]`. В отличие от
   неё, префиксы Killstreak/Australium/Festive здесь не срезаются —
   PriceDB.io ожидает полное человеческое имя (как market_hash_name), а не
   голое название оружия. Unusual-предметы (для них имя без названия
   эффекта не резолвится, см. `buildPriceableName`) живым HTML под `/stats`
   не проверялись — в этом случае `resolveSku` просто вернёт `null`, и
   график тихо не появится, без ошибки.

**Без MutationObserver** — как и `bptf-ks-tier-buttons`: `<h2
id="classifieds">` и всё, что перед ней, отдаётся сервером сразу в исходном
HTML страницы (подтверждено обоими живыми дампами), AJAX'ом на `/stats`
подгружаются только сами объявления внутри секции (см. раздел
`bptf-listing-trade-params` выше), не сама секция и не её заголовок. Одного
прохода при старте content-скрипта достаточно.

**Только classic backpack.tf `/stats/*`** — без `/classifieds*` (страница
поиска по всем предметам сразу, там нет ни одного конкретного SKU для
графика) и без next.backpack.tf (разметка там не проверялась — тот же
принцип "только подтверждённое живым HTML", что и у `bptf-filter-special`/
`bptf-ks-tier-buttons`).

- **Ссылки на профиле backpack.tf** (`bptf-profile-links` — liquid.tf/

- **Итог в ключах вместо refined** (`bptf-keys-total`, backpack.tf).

### Требование 6 (иконки) — план и фактическая реализация

Изначально планировался гибрид: бандлить spell/parts/killstreak иконки
внутрь расширения, а unusual-эффекты (их ~540, не ~600 — см.
`utils/unusual-effects.ts`) хотлинкать на itempedia.tf. По факту
unusual-эффекты хотлинкаются на исходные хосты (itempedia.tf) — та же
ссылка, что открывает оригинал, надёжнее гарантирует пиксельную
идентичность, чем своя копия. Сеть сборочной среды на момент разработки
также не позволяла скачать сторонние (Flaticon) байты для бандлинга —
spell/killstreak-иконки поэтому нарисованы вручную как SVG
(`utils/spell-icons.ts`) по референсам, присланным заказчиком, вместо
хотлинка или бандлинга готовых файлов; это уже не «точь-в-точь как в
оригинале» (который просто рисует общий бейдж), а расширение сверх
ТЗ — режим «Просто» в настройках модуля даёт поведение, эквивалентное
оригиналу, для тех, кому это важнее.

Резолвер `utils/item-attributes.ts` + рендерer
`utils/item-attribute-render.ts` общий — `trade-item-attributes` (окно
трейд-оффера), `inventory-item-attributes` (инвентарь) и
`market-item-attributes` (листинги Market) все три его используют:
парсинг атрибутов предмета и отрисовка значков не дублируются между
страницами. (`showcase-item-attributes` — планировавшийся четвёртый
потребитель этой же пары утилит, витрина профиля Steam — по прямой
просьбе пользователя убран из реестра и реализовываться не будет, см.
«Функции, которые решено не реализовывать» выше.)

### Загрузка неупакованного расширения

**Chrome / Edge / Brave / Opera:**
`chrome://extensions` → включить «Режим разработчика» → «Загрузить
распакованное расширение» → выбрать `.output/chrome-mv3`.

**Firefox:**
`about:debugging#/runtime/this-firefox` → «Загрузить временное дополнение»
→ выбрать любой файл внутри `.output/firefox-mv2` (например
`manifest.json`).

### Как добавить новый модуль

1. Добавить запись в `FEATURE_REGISTRY` (`utils/registry.ts`) —
   `id`, `site`, `title`/`description` как `LocalizedText` (оба языка
   сразу, не только русский), `defaultEnabled`, `status: 'planned'`,
   честный `portedFrom` (проверить, нет ли уже похожей функции у другого
   модуля — требование 4; поле по-прежнему заполняется, хотя на карточке
   больше не отображается, см. «Локализация» выше), при необходимости
   `stability` (известное ограничение — тоже `LocalizedText`) и
   `dependsOn` (если модуль реально зависит от другого).
2. Создать `modules/<id>/` — как минимум `panel.ts` + `panel.css`
   (использовать классы/токены из `styles/tokens.css`); если нужен
   доступ к `window.*` страницы — добавить `core.ts` и `types.ts` по
   образцу `modules/wallet-summary/`. Любой видимый пользователю текст —
   через локальный `const UI = { ru: {...}, en: {...} } as const` рядом с
   кодом (см. «Локализация» выше), не голыми строками; экспортируемые
   функции модуля получают `locale: Locale` последним параметром.
3. Завести content-скрипт(ы) в `entrypoints/` с нужным `matches`, для
   ISOLATED-скрипта — обязательно проверка `isFeatureEnabled(id)` и
   `getLocale()`, подписка через `watchSettings` с обработкой и
   вкл/выкл, и смены `settings.locale` (полный `stop()`/`start(locale)`
   или `ui.remove()`/`ui.mount()` — см. «Локализация» выше за тем, почему
   именно полный remount, а не точечное обновление текста), монтаж через
   `createShadowRootUi`.
4. Поменять `status` на `'ready'` в реестре, когда модуль реализован.

Тумблер в options/popup для новой функции появится сам — ничего в Vue
менять не требуется.
